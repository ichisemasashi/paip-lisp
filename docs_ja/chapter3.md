# 第3章

## Lispの概要

> 間違いない。
> Common Lispは「巨大な」言語である。
> — Guy L. Steele, Jr.
> *Koschman 1990* 序文より

この章では、Lispにおける最も重要な特殊形式と関数を簡潔に取り上げる。
経験豊富なCommon Lispプログラマにとっては、この章は読み飛ばすかざっと目を通す程度でよいが、初心者のLispプログラマ、あるいはCommon Lisp方言に初めて触れる人にとっては必読である。

この章はリファレンスとして利用できるが、最も権威あるリファレンスはSteeleによる *Common Lisp the Language* 第2版であり、疑問が生じた場合にはそれを参照すべきである。
この章の25倍もの長さがあるその書籍と比べれば、ここでは重要な要点に触れるにとどまることは明らかである。
各機能が実際のプログラムで使用される際には、本書の後半でより詳細に解説される。

## 3.1 Lispスタイルの指針

初学者のCommon Lispプログラマは、言語が提供する多くの選択肢に圧倒されがちである。
この章では、リストの長さを求めるための14通りの異なる方法を示す。
では、プログラマはどの方法を選ぶべきなのだろうか？
ひとつの答えは、この本で示されているように、優れたプログラムの例を読み、そのスタイルを模倣することである。
一般的に、すべてのプログラマが従うべき6つの格言がある。

* 具体的であれ。
* 抽象を使え。
* 簡潔であれ。
* 用意された道具を使え。
* わかりにくくするな。
* 一貫性を保て。

これらには多少の説明が必要である。

できるかぎり具体的な形式を使うことは、読者があなたの意図を理解しやすくする。
たとえば、条件式の特殊形式 `when` は `if` よりも具体的である。
`when` を見た読者は、「テストが真のときに実行される節」だけを探せばよいとわかる。
一方、`if` を見た読者は、テストが真のときの節と偽のときの節の2つを当然期待する。
たとえ節が1つしかない場合でも、`if` よりも `when` を使うほうが望ましい。なぜなら `when` のほうがより具体的だからである。

具体的であるための重要な方法の1つは、抽象を使うことである。
Lispはリストや配列といった非常に一般的なデータ構造を提供する。
これらを使って、プログラムで利用する特定のデータ構造を実装することができるが、原始的な関数を直接呼び出すという誤りを犯してはならない。
もし次のように名前のリストを定義したなら：

```lisp
(defvar *names* '((Robert E. Lee) ...))
```

各名前の構成要素を取得するための関数も定義すべきである。
`Lee` を取り出すには、`(caddar *names*)` ではなく `(last-name (first *names*))` を使うべきである。

多くの場合、これらの格言は調和している。
たとえば、リスト内の要素を探すコードを書く場合、`loop` や `do` ではなく `find`（あるいは場合によっては `find-if`）を使うべきである。
`find` は `loop` や `do` といった一般的な構文よりも具体的であり、抽象化され、簡潔であり、組み込みのツールであり、理解しやすい。

しかし時として、これらの格言が互いに衝突することがある。
その場合、どちらを優先すべきかは経験によって判断される。
次の2つの方法で、新しいキーと値のペアを連想リストに追加する例を考えてみよう：<sup>[1](#fn03-1)</sup>

```lisp
(push (cons key val) a-list)
(setf a-list (acons key val a-list))
```

最初のもののほうが簡潔である。
しかし2番目のものはより具体的である。なぜなら `acons` 関数は、連想リスト専用に設計されているからである。
どちらを選ぶかは、おそらく「わかりにくさ」にかかっている。
`acons` に親しみを感じる人なら2番目を好み、`acons` がわかりにくいと感じる人は1番目を好むだろう。

同様の選択は、変数に値を設定する場合にも生じる。
最も具体的であるという理由から `(setq x val)` を好む人もいれば、すべての更新に対して1つの形式 `setf` を使うほうが一貫していると感じ、`(setf x val)` を使う人もいる。
どちらを選ぶにせよ、6番目の格言を忘れてはならない。
**一貫性を保て。**

## 3.2 特殊形式（Special Forms）

[第1章](chapter1.md) で述べたように、「特殊形式（special form）」という用語は、Common Lisp の構文的構成要素と、それを示す予約語の両方を指すために使われる。

最も一般的に使われる特殊形式は以下のとおりである：

| 定義関連           | 条件分岐     | 変数     | 反復        | その他        |
| -------------- | -------- | ------ | --------- | ---------- |
| `defun`        | `and`    | `let`  | `do`      | `declare`  |
| `defstruct`    | `case`   | `let*` | `do*`     | `function` |
| `defvar`       | `cond`   | `pop`  | `dolist`  | `progn`    |
| `defparameter` | `if`     | `push` | `dotimes` | `quote`    |
| `defconstant`  | `or`     | `setf` | `loop`    | `return`   |
| `defmacro`     | `unless` | `incf` |           | `trace`    |
| `labels`       | `when`   | `decf` |           | `untrace`  |

正確に言うと、`declare`、`function`、`if`、`labels`、`let`、`let*`、`progn`、そして `quote` だけが真の特殊形式である。
その他のものは、実際にはより基本的な特殊形式や関数への呼び出しに展開されるマクロとして定義されている。
プログラマにとっては実質的な違いはなく、Common Lisp の実装はマクロを特殊形式として、またはその逆として実装することも自由である。
したがって、以後は簡単のために、「特殊形式」という語を真の特殊形式および組み込みマクロの両方を包括する用語として用いることにする。

---

### 定義のための特殊形式

この節では、新しいグローバル関数・マクロ・変数・構造体を導入するために使用できる特殊形式を概観する。
関数を定義するための `defun` 形式はすでに見た。
`defmacro` 形式はそれと類似しており、[66ページ](#p66) で扱われる。

> `(defun` *function-name (parameter...) "optional documentation" body...*)
>
> `(defmacro` *macro-name (parameter...) "optional documentation" body...*)

特殊変数を導入するための形式は3つある。
`defvar` は特殊変数を定義し、必要に応じて初期値およびドキュメンテーション文字列を与えることができる。
初期値は、その変数がまだ値を持たない場合にのみ評価され、代入される。
`defparameter` も似ているが、こちらでは値が必須であり、既存の値があればそれを上書きする。
`defconstant` は、シンボルが常に特定の値を表すことを宣言するために使われる。

> `(defvar` *variable-name initial-value "optional documentation"*)
>
> `(defparameter` *variable-name value "optional documentation"*)
>
> `(defconstant` *variable-name value "optional documentation"*)

これらすべての `def-` 形式はグローバルなオブジェクトを定義する。
後で見るように、`let` を使ってローカル変数を定義したり、`labels` を使ってローカル関数を定義することもできる。

---

ほとんどのプログラミング言語は、関連するデータを1つの構造体としてまとめる手段を提供している。
Common Lisp も例外ではない。
`defstruct` 特殊形式は、構造体型（Pascal における *record* 型に相当）を定義し、その構造体の要素へアクセスするための関数を自動的に生成する。
一般的な構文は次のとおりである。

> `(defstruct` *structure-name "optional documentation" slot...*)

たとえば、名前を表す構造体を定義することができる：

```lisp
(defstruct name
  first
  (middle nil)
  last)
```

これにより、コンストラクタ関数 `make-name`、認識述語 `name-p`、およびアクセサ関数 `name-first`、`name-middle`、`name-last` が自動的に定義される。
`(middle nil)` は、`make-name` によって新しく作られる各 name 構造体の middle フィールドがデフォルトで `nil` になることを意味している。
以下に、構造体を作成し、アクセスし、変更する例を示す：

```lisp
> (setf b (make-name :first 'Barney :last 'Rubble)) =>
#S(NAME :FIRST BARNEY :LAST RUBBLE)

> (name-first b) => BARNEY

> (name-middle b) => NIL

> (name-last b) => RUBBLE

> (name-p b) => T

> (name-p 'Barney) => NIL ; make-name の結果だけが name として認識される

> (setf (name-middle b) 'Q) => Q

> b => #S(NAME :FIRST BARNEY :MIDDLE Q :LAST RUBBLE)
```

構造体の印字表現は `#S` で始まり、構造体の型、およびスロット名と値のペアのリストが続く。
この表現に惑わされてはいけない。これは構造体を表示するための便利な形式にすぎず、内部的な表現を正確に反映しているわけではない。
実際、構造体はベクタに非常によく似た形で実装されている。
`name` 構造体の場合、型はベクタの0番目の要素に、first は1番目、middle は2番目、last は3番目の要素に格納される。
したがって、構造体はリストよりも効率的である。
構造体はより少ないメモリを使用し、どの要素にも1ステップでアクセスできる。
一方、リストの場合、*n* 番目の要素にアクセスするには *n* ステップが必要である。

構造体およびそのスロットに対する制御をより細かく行うためのオプションも存在する。
それらについては後の章で、必要に応じて取り上げる。

### 条件分岐のための特殊形式（Special Forms for Conditionals）

私たちはすでに特殊形式 `if` を見てきた。
その構文は (`if` *test then-part else-part*) の形をしており、*test* の結果が真であるか偽であるかによって、*then-part* あるいは *else-part* のどちらかが値として返される。
条件式において偽と見なされるのは `nil` のみであり、その他のすべての値は真とみなされることを覚えておこう。
ただし、定数 `t` は（特別な理由がない限り）真を表すための慣用的な値として使われる。

実際のところ、条件付き評価を行う特殊形式はかなり多い。
厳密に言えば、`if` は特殊形式として定義されているが、他の条件構文はマクロである。したがって、ある意味では `if` が最も基本的な形式とされる。
多くの条件を `if` で記述することを好むプログラマもいれば、もっと古くからあり汎用的（ただし見た目が必ずしも美しくはない）な `cond` を好むプログラマもいる。
最後に、英語の文章のようなスタイルを好み、`when`、`unless`、`if` などを自由に使うプログラマもいる。

以下の表は、それぞれの条件構文がどのように `if` および `cond` によって表現できるかを示している。
もっとも、これらの変換は完全に正しいわけではない。なぜなら、`or`、`case`、および `cond` は同じ式を複数回評価しないように設計されているのに対し、`if` を使った翻訳では、式が複数回評価される可能性があるからである。
この表には `cond` への翻訳も併記されている。
`cond` の構文は、*cond-clause* と呼ばれるテスト式とその結果式群の並びである。

```
(cond (test result...)
      (test result...)
      ...)
```

`cond` は cond-clause を1つずつ順に評価していく。
最初にテスト式が非 `nil` に評価された節が見つかると、その節内の結果式が順に評価され、最後の式の値が `cond` 全体の値として返される。
特に、cond-clause がテスト式だけを含み結果式を持たない場合、そのテスト式が非 `nil` であればその値自体が `cond` の値となる。
すべてのテスト式が `nil` に評価された場合、`cond` の値は `nil` となる。
よく使われる慣用表現として、最後の cond-clause を `(t` *result...* ) にすることが多い。

---

`when` と `unless` は、単一の `cond` 節のように動作する。
どちらの形式も、テスト式のあとに1つ以上の結果式が続き、テストが満たされた場合にそれらが評価される。
つまり、`when` はテストが真のとき、`unless` はテストが偽のときに結果式を評価する。

---

`and` は複数の条件のすべてが真であるかどうかをテストし、`or` はそのうちの少なくとも1つが真であるかどうかをテストする。
どちらも引数を左から右へ評価し、結果が確定した時点で評価を停止する。
以下にそれぞれの等価表を示す。

| 条件構文                           | `if` での表現                           | `cond` での表現                           |
| ------------------------------ | ----------------------------------- | ------------------------------------- |
| `(when` *test a b c*)          | `(if` *test* `(progn` *a b c*))     | `(cond` (*test a b c*))               |
| `(unless` *test x y*)          | `(if (not` *test*) `(progn` *x y*)) | `(cond ((not` *test*) *x y*))         |
| `(and` *a b c*)                | `(if` *a* `(if` *b c*))             | `(cond` (*a* `(cond` (*b c*))))       |
| `(or` *a b c*)                 | `(if` *a a* `(if` *b b c*))         | `(cond (a)` (*b*) (*c*))              |
| `(case` *a* (*b c*) (`t` *x*)) | `(if (eql` *a 'b*) *c x*)           | `(cond ((eql` *a 'b*) *c*) (`t` *x*)) |

---

`and` や `or` を論理条件のテスト以外の用途に使うのは悪いスタイルとされている。
条件に基づいて処理を行う場合には、`when`、`unless`、または `if` を使うべきである。
次に例を示す：

```lisp
(and (> n 100)
     (princ "N is large."))   ; 悪いスタイル！
(or (<= n 100)
    (princ "N is large."))    ; さらに悪いスタイル！
(cond ((> n 100)              ; 悪くはないが私の好みではない
      (princ "N is large."))
(when (> n 100)
  (princ "N is large."))      ; 良いスタイル。
```

---

主な目的が処理を行うことではなく値を返すことである場合、`when` や `unless` よりも `cond` や `if`（else節で明示的に `nil` を返す）を使うほうが望ましい。
`when` や `unless` は else 節で暗黙的に `nil` を返すためである。
`when` や `unless` は可能性が1つしかない場合に適しており、2つの可能性がある場合は `if`（あるいは好みによって `cond`）を、3つ以上ある場合には `cond` を使うのがよい。

```lisp
(defun tax-bracket (income)
  "この所得に対して支払うべき税率を求める。"
  (cond ((< income 10000.00) 0.00)
        ((< income 30000.00) 0.20)
        ((< income 50000.00) 0.25)
        ((< income 70000.00) 0.30)
        (t                   0.35)))
```

---

もし、いくつかのテストが同じ式を異なる定数と比較している場合には、`case` が適している。
`case` の構文は次のようになる。

> `(case` *expression* 
> 　　(*match result*...)...)

*expression* が評価され、各 *match* と順に比較される。
1つが `eql` で一致した時点で、その節の *result* 式が順に評価され、最後の式の値が返される。
なお、*match* 式自体は評価されない。
*match* 式がリストの場合、`case` は *expression* がそのリストのいずれかの要素と `eql` であるかどうかをテストする。
*match* 式がシンボル `otherwise`（またはシンボル `t`）である場合、それはどんな値にもマッチする。
（この `otherwise` 節は最後に置くのが理にかなっている。）

---

もう1つの特殊形式 `typecase` もあり、これは式の型をいくつかの候補と比較し、`case` と同様に最初に一致する節を選ぶ。
さらに、`ecase` および `etypecase` は、それぞれ `case` および `typecase` に似ているが、一致する節がない場合にはエラーを通知する。

ここでの `e` は、「exhaustive（包括的）」あるいは「error（エラー）」の意味と考えることができる。
`ccase` および `ctypecase` もエラーを通知するが、これらは「継続可能なエラー」（致命的でないエラー）を発生させることができる。
ユーザには、マッチ条件を満たすように式を修正する機会が与えられる。

以下に、`case` 系の形式とそれに対応する `cond` 表現の例を示す：

| 形式                   | `cond` による等価表現                     |
| -------------------- | ---------------------------------- |
| `(case x`            | `(cond`                            |
| `(1 10)`             | `((eql x 1) 10)`                   |
| `(2 20))`            | `((eql x 2) 20))`                  |
|                      |                                    |
| `(typecase x`        | `(cond`                            |
| `(number (abs x))`   | `((typep x 'number) (abs x))`      |
| `(list (length x)))` | `((typep x 'list) (length x)))`    |
|                      |                                    |
| `(ecase x`           | `(cond`                            |
| `(1 10)`             | `((eql x 1) 10)`                   |
| `(2 20))`            | `((eql x 2) 20)`                   |
|                      | `(t (error "no valid case")))`     |
|                      |                                    |
| `(etypecase x`       | `(cond`                            |
| `(number (abs x))`   | `((typep x 'number) (abs x))`      |
| `(list (length x)))` | `((typep x 'list) (length x))`     |
|                      | `(t (error "no valid typecase")))` |

### 変数と場所を扱うための特殊形式（Special Forms for Dealing with Variables and Places）

特殊形式 `setf` は、他の言語における `=` や `:=` による代入文と同様に、変数または *場所（place）* に新しい値を代入するために使われる。
「場所」または *一般化変数（generalized variable）* とは、値を格納できる領域に対する名前である。
以下は、Lisp と Pascal における対応する代入形式の例である。

| []()                        |                      |
| --------------------------- | -------------------- |
| `;; Lisp`                   | `/* Pascal */`       |
| `(setf x 0)`                | `x := 0;`            |
| `(setf (aref A i j) 0)`     | `A[i,j] := 0;`       |
| `(setf (rest list) nil)`    | `list^.rest := nil;` |
| `(setf (name-middle b) 'Q)` | `b\middle := "Q";`   |

`setf` は変数を設定するだけでなく、構造体の一部（コンポーネント）を設定するためにも使用できる。
Pascal のような言語では、代入文の左辺に現れる式は言語仕様によって制限されている。
一方 Lisp では、特殊形式 `defsetf` または `define-setf-method` を用いることで、`setf` の左辺に使用できる式を拡張することができる。
これらはそれぞれ [514ページ](chapter15.md#p514) および [884ページ](chapter25.md#p884) で紹介される。

---

また、場所を変更するための組み込み関数もいくつか存在する。
たとえば、`(rplacd list nil)` は `(setf (rest list) nil)` と同じ効果を持つが、`nil` の代わりに `list` を返す点が異なる。
多くの Common Lisp プログラマは、特殊化された関数よりも `setf` 形式を使うことを好む。

単に変数に値を設定したいだけの場合には、特殊形式 `setq` を代わりに使うこともできる。
しかし本書では、特異性よりも一貫性を重視し、すべての場合で `setf` を使用することにする。

---

この節の説明では、変数（および構造体のスロット）が常に新しい値を代入されるような印象を与えるかもしれない。
しかし実際には、多くの Lisp プログラムでは代入を一切行わない。
Lisp はしばしば *関数型スタイル* で使用される。すなわち、新しい変数を導入することはあっても、一度値が束縛された変数は変更されない、というスタイルである。

新しい変数を導入する方法のひとつは、関数のパラメータとして定義することである。
また、特殊形式 `let` を使ってローカル変数を導入することもできる。
`let` の一般的な形式とその例を次に示す。
各変数は対応する値に束縛され、その後で本体（body）が評価される。

> `(let` ((*variable value*)...) 
> *body*...)

```lisp
(let ((x 40)
       (y (+ 1 1)))
  (+ x y)) => 42
```

---

`let` 形式によってローカル変数を定義することは、無名関数のパラメータを定義するのと実質的に同じである。
前者は次のような形に等しい：

| []()                        |
| --------------------------- |
| ((`lambda` (*variable*... ) |
| `  ` *body*... )            |
| *value*...)                 |

```lisp
((lambda (x y)
     (+ x y))
40
(+ 1 1))
```

まずすべての値が評価され、それからそれらが変数（すなわちラムダ式のパラメータ）に束縛される。
最後に、その束縛を用いて本体が評価される。

---

特殊形式 `let*` は、新たに導入された変数を後続の *value* の計算で使用したい場合に適している。
たとえば次のようになる。

```lisp
(let* ((x 6)
       (y (* x x)))
  (+ x y)) => 42
```

ここでは `let` を使うことはできない。
なぜなら、その場合 `y` の値を計算するときに変数 `x` はまだ束縛されていないためである。

---

▣ **演習 3.1 [m]**
上の `let*` 式と等価な `lambda` 式を示せ。
必要に応じて複数の `lambda` を使ってもよい。

---

Lisp においてリストは非常に重要であるため、リストの先頭に要素を追加・削除するための特殊形式、すなわちリストをスタックとして扱うための形式が用意されている。
もし `list` がリストを保持している場所の名前であるならば、`(push x list)` は `list` の先頭に *x* を追加し、`(pop list)` は最初の要素を返すと同時に、副作用として `list` からその要素を削除する。
`push` と `pop` は以下の式と等価である。

```lisp
(push x list) ≡ (setf list (cons x list))
(pop list)    ≡ (let ((result (first list)))
                 (setf list (rest list))
                 result)
```

---

リストが要素を蓄積するのに使われるように、加算変数も数値を蓄積するために使うことができる。
Lisp には、合計を増減させるための2つの特殊形式 `incf` と `decf` が用意されている。
どちらの形式も第1引数は「場所」（変数または `setf` で代入可能な式）であり、第2引数はオプションで、増減させる数を指定する。
C 言語に詳しい人なら、`(incf x)` は `++x`、`(incf x 2)` は `x += 2` に相当すると理解できる。
Lisp での等価関係は次のとおりである。

```lisp
(incf x) ≡ (incf x 1) ≡ (setf x (+ x 1))
(decf x) ≡ (decf x 1) ≡ (setf x (- x 1))
```

---

場所が単なる変数ではなく複合式である場合、Lisp は展開時に注意深くコードを生成し、部分式が複数回評価されないようにする。
この性質は `push`、`pop`、`incf`、および `decf` すべてに共通している。

次の例では、プレイヤーのリストがあり、スコアの最も高いプレイヤー（すなわち勝者）を決定したいとする。
構造体 `player` には、プレイヤーのスコアと勝利数のスロットがあり、関数 `determine-winner` は勝者の `wins` フィールドを1増やす。
`incf` の展開では、一時変数が束縛されることでソート処理が2回行われないようにしている。

```lisp
(defstruct player (score 0) (wins 0))

(defun determine-winner (players)
  "スコアが最も高いプレイヤーの WINS を1増やす。"
  (incf (player-wins (first (sort players #'>
                                  :key #'player-score)))))

(defun determine-winner (players)
   "スコアが最も高いプレイヤーの WINS を1増やす。"
   (let ((temp (first (sort players #'> :key #'player-score))))
      (setf (player-wins temp) (+ (player-wins temp) 1))))
```

### 繰り返しのための関数と特殊形式（Functions and Special Forms for Repetition）

多くのプログラミング言語には、反復ループを作るための予約語が少数しか存在しない。
たとえば、Pascal には `while`、`repeat`、`for` 文がある。
対照的に、Common Lisp では、ほとんど目が回るほど多様な選択肢が存在する。以下にその概要を示す。

| []()              | 説明                  |
| ----------------- | ------------------- |
| `dolist`          | リストの要素を順にループする      |
| `dotimes`         | 連続する整数に対してループする     |
| `do, do*`         | 一般的なループ（簡潔な構文）      |
| `loop`            | 一般的なループ（冗長な構文）      |
| `mapc, mapcar`    | リストの要素に関数を適用してループする |
| `some, every`     | 条件が満たされるまでリストをループする |
| `find, reduce` など | より特化されたループ関数        |
| *recursion*       | 一般的な繰り返し            |

---

それぞれの手法を説明するために、リストの要素数を返す関数 `length` のいくつかのバージョンを示す。
まず、特殊形式 `dolist` はリストの要素を順に処理するために使える。構文は次の通りである。

> `(dolist (`*variable list optional-result*) *body...*)`

これは、*list* の各要素に対して1回ずつ *body* が実行されることを意味する。
このとき *variable* には、最初の要素、次の要素…というように順に束縛される。
最後に、`dolist` は *optional-result* を評価してその値を返す。結果式がなければ `nil` が返される。

---

以下は `dolist` を使った `length` の定義である。
`let` 形式で新しい変数 `len` を導入し、最初に 0 に束縛する。
`dolist` はリストの各要素に対して本体を実行し、そのたびに `len` を1増やす。
この例では、繰り返し変数 `element` が本体内で使われていない点が少し特殊である。

```lisp
(defun length1 (list)
  (let ((len 0))            ; LEN=0 で開始
    (dolist (element list)  ; 各要素に対して
      (incf len))           ; LEN を 1 増加
    len))                   ; LEN を返す
```

---

また、`dolist` のオプションの結果式を使うこともできる。以下に例を示す。
このスタイルを好むプログラマも多いが、結果が見えにくくなるため、私は結果を最後に明示的に置く方を好む。

```lisp
(defun length1.1 (list)         ; 代替版（好みではない）
  (let ((len 0))
    (dolist (element list len)  ; len を結果として使用
      (incf len))))
```

---

関数 `mapc` は、特殊形式 `dolist` とほぼ同じ動作をする。
最も単純な場合、`mapc` は2つの引数を取る。
最初の引数は関数で、2番目はリストである。
リストの各要素に関数を適用する。以下は `mapc` を使った `length` の例である。

```lisp
(defun length2 (list)
  (let ((len 0))                    ; LEN=0 で開始
    (mapc #'(lambda (element)       ; 各要素に対して
              (incf len))           ; LEN を 1 増加
          list)
    len))                           ; LEN を返す
```

マッピング関数は全部で7種類あり、その中でも最も有用なのは `mapc` と `mapcar` である。
`mapcar` は `mapc` と同じ関数呼び出しを行うが、結果をリストとして返す。

---

また、`dotimes` 形式も存在する。構文は次の通りである。

> (`dotimes` (*variable number optional-result*) *body...*)

これは、*variable* に 0 から *number*-1 までの値を順に束縛しながら本体を実行する（合計 *number* 回繰り返す）。
もちろん、`length` の実装には向いていない。なぜなら、繰り返し回数が事前にわからないからである。

---

次に、より一般的なループ構文として `do` と `loop` がある。
`do` の構文は次のようになる。

```lisp
(do ((variable initial next)...)
    (exit-test result)
  body...)
```

各 *variable* は最初に *initial* 値に束縛される。
*exit-test* が真であれば、*result* が返される。
そうでない場合は本体が実行され、各 *variable* が対応する *next* の値に更新されて再びテストされる。
このループは *exit-test* が真になるまで続く。
もし *next* の値が省略された場合、その変数は更新されず、`let` で束縛されたかのように扱われる。

---

以下は `do` を使った `length` の実装例である。
ここでは、要素数を数えるための変数 `len` と、リストを順に辿るための変数 `l` の2つを使う。
このように `cdr` を繰り返してリストを辿ることを「リストを cdr する（*cdr-ing down a list*）」という。
（ここではより覚えやすい `rest` を使用している。）
この `do` ループには本体が存在しない点に注意。
すべての処理は初期化部、更新部、終了判定で行われている。

```lisp
(defun length3 (list)
  (do ((len 0 (+ len 1))   ; LEN=0 で開始、毎回 +1
       (l list (rest l)))  ; リストを1段階ずつ進める
      ((null l) len)))     ; リストの終端で LEN を返す
```

`do` 形式は、リストをループしていることが明確でないため、少しわかりにくい。
リストを辿っていることを理解するには、変数 `l` と終了条件の両方を見る必要がある。
さらに、現在の要素を指す変数がないため、要素を取得するには `(first l)` と書かなければならない。
一方、`dolist` や `mapc` はステップ処理・終了判定・変数名の管理を自動で行ってくれる。
これらは「具体的であれ（be specific）」という原則の好例である。
`do` は汎用的すぎるため、本書ではあまり使用しない。
ただし、多くの優れたプログラマが使うため、少なくとも `do` を読む方法は知っておくべきである。

---

`loop` の構文はそれ自体が1つの小さな言語であり、しかも Lisp 的でないとよく言われる。
ここではその全機能を列挙する代わりに、例のみを示し、詳細は *Common Lisp the Language (第2版)* または第24.5章を参照してほしい。

以下は `loop` を使った `length` の3つの例である。

```lisp
(defun length4 (list)
  (loop for element in list      ; 各要素を順に処理
        count t))                ; 1つずつ数える

(defun length5 (list)
  (loop for element in list      ; 各要素を順に処理
        summing 1))              ; 毎回1を加算する

(defun length6 (list)
  (loop with len = 0             ; LEN=0 で開始
        until (null list)        ; リストの終端まで
        for element = (pop list) ; 各反復で要素を取り出す
        do (incf len)            ; LEN を 1 増やす
        finally (return len)))   ; 最後に LEN を返す
```

---

どのプログラマも、繰り返し使われる特定のループパターンを学ぶ。
これらは一般に *programming idioms*（プログラミングイディオム）または *clichés*（常套句）と呼ばれる。
典型的な例は、リストや配列のすべての要素を処理するような場合である。
多くの言語では、このようなイディオムに特有の構文は存在せず、一般的なループ構文を使い、プログラムの読者が意図を読み取らなければならない。

Lisp が他と異なるのは、こうしたイディオムを明示的にカプセル化し、構文的にも関数的にも直接参照できる点である。
`dolist` と `dotimes` はその代表例であり、どちらも「具体的であれ（be specific）」という原則に従っている。
多くのプログラマは、同等の `do` よりも `dolist` を使うことを好む。
なぜなら、`dolist` は「このループはリストの要素を順に処理している」と明確に示しているからである。
もちろん、対応する `do` 形式でも同じことはできるが、読者がそれを理解するにはより多くの手間がかかる。

---

`dolist` や `dotimes` のような特殊形式に加えて、一般的なイディオムを扱うための関数も多数存在する。
その中でも `count-if`（述語を満たす要素の数を数える）と `position-if`（述語を満たす要素のインデックスを返す）は代表的である。
どちらも `length` の実装に利用できる。

以下の `length7` では、`count-if` が述語 `true` を満たす要素の数を返す。
`true` は常に真を返す関数なので、結果的にリストの長さが得られる。

```lisp
(defun length7 (list)
  (count-if #'true list))

(defun true (x) t)
```

`length8` では、`position-if` 関数が述語 `true` を満たす要素の位置をリストの末尾から検索する。
これはリストの最後の要素の位置となり、インデックスが0から始まるため、1を加えることでリストの長さを得る。
もっとも、これはあまり素直な `length` の実装とは言えない。

```lisp
(defun length8 (list)
  (if (null list)
      0
      (+ 1 (position-if #'true list :from-end t))))
```

### 再帰による繰り返し（Repetition through Recursion）

Lisp は「再帰的な（recursive）」言語として知られている。
これは、Lisp がプログラマに「自分自身を呼び出す関数」を書くことを奨励するという意味である。
これまで見てきたように、Common Lisp にはループを書くための関数や特殊形式が目が回るほど多く存在する。
しかし、多くのプログラムは構文的なループではなく、**再帰**によって繰り返しを処理していることも事実である。

---

`length` の単純な定義のひとつは次のように表せる：

> 「空リストの長さは 0 であり、それ以外のリストの長さは、リストの残り部分（最初の要素を除いた部分）の長さに 1 を加えたものである。」

この定義は、直接的に次のような再帰関数に翻訳できる：

```lisp
(defun length9 (list)
  (if (null list)
      0
      (+ 1 (length9 (rest list)))))
```

---

この `length` のバージョンは、リストの再帰的定義から自然に導かれる：

> 「リストとは、空リストであるか、ある要素が別のリストに `cons` されたものである。」

一般的に、ほとんどの再帰関数は、操作対象となるデータの再帰的性質に由来する。
たとえば二分木のようなデータは、再帰的な方法でしか扱いにくい。
一方で、リストや整数のようなデータは、再帰的にも（再帰関数に導かれる）、
または連続的なシーケンスとしても（反復関数に導かれる）定義できる。

本書では、「リストをシーケンスとして扱う（list-as-sequence）」見方を主に採用している。
「リストを最初の要素と残りに分ける（list-as-first-and-rest）」見方を取らない理由は、
それが Lisp の内部実装に依存した恣意的で人工的な区分だからである。
リストの分解方法は他にも多くある。
たとえば、「最後の要素」と「それ以外の要素」に分けたり、「前半」と「後半」に分けることもできる。
「リスト＝シーケンス」的な見方は、このような人工的区別を設けず、すべての要素を等しく扱う。

---

再帰関数の使用に対してよくある反論は、「非効率的である」というものである。
なぜなら、コンパイラは再帰呼び出しごとにメモリを割り当てる必要があるからだ。
これは `length9` の場合には確かに当てはまるが、すべての再帰関数に当てはまるわけではない。
次の定義を考えてみよう：

```lisp
(defun length10 (list)
  (length10-aux list 0))

(defun length10-aux (sublist len-so-far)
  (if (null sublist)
      len-so-far
      (length10-aux (rest sublist) (+ 1 len-so-far))))
```

`length10` は補助関数 `length10-aux` を呼び出し、リストのこれまでの長さとして 0 を渡している。
`length10-aux` はリストの末尾まで進みながら、各要素ごとに 1 を加算する。
ここでの**不変関係（invariant relation）**は、
「部分リストの長さ ＋ `len-so-far` ＝ 元のリストの長さ」である。
したがって、部分リストが `nil` になったとき、`len-so-far` が元のリストの長さを表す。

このように、部分結果を保持するための変数（`len-so-far` のようなもの）を **アキュムレータ（accumulator）** と呼ぶ。
アキュムレータを使う関数の他の例としては、
p.329 の `flatten-all`、p.237 の `one-unknown`、p.686 の Prolog の述語、
そして p.400 および p.433 の `anonymous-variables-in`（これは2つのアキュムレータを使用）などがある。

---

`length9` と `length10` の重要な違いは、**加算を行うタイミング**である。

* `length9` では、関数が自分自身を呼び出し、その後で戻り、そして最後に 1 を加える。
* 一方、`length10-aux` では、まず 1 を加え、それから自分自身を呼び出し、戻る。

`length10-aux` では、再帰呼び出しの後に行うべき操作が残っていないため、
コンパイラは再帰呼び出し前に元の呼び出しに割り当てたメモリを解放することができる。
このような関数を **末尾再帰（tail-recursive）** 関数と呼ぶ。
なぜなら、再帰呼び出しが関数の最後の操作（末尾）として現れるからである。

多くのコンパイラは末尾再帰を最適化する（ただし、すべてのコンパイラがそうするわけではない）。
（[第22章](chapter22.md) では末尾再帰をさらに詳しく扱い、Scheme のコンパイラが末尾再帰最適化を保証していることを指摘している。）

---

`length10-aux` を導入するのは見た目が美しくないと感じる人もいる。
そのような場合には、2つの代替案がある。

まず1つ目は、`length10` と `length10-aux` を統合して、
オプション引数を持つ単一の関数として書く方法である。

```lisp
(defun length11 (list &optional (len-so-far 0))
  (if (null list)
      len-so-far
      (length11 (rest list) (+ 1 len-so-far))))
```

---

2つ目は、メイン関数の定義の内部に**ローカル関数**を導入する方法である。
これは特殊形式 `labels` を使って行う。

```lisp
(defun length12 (the-list)
  (labels
    ((length13 (list len-so-far)
       (if (null list)
           len-so-far
           (length13 (rest list) (+ 1 len-so-far)))))
    (length13 the-list 0)))
```

一般に、`labels` 形式（または類似の `flet` 形式）は、1つ以上のローカル関数を導入するために使用できる。
その構文は次のようになる：

```
(labels
  ((function-name (parameter...) function-body)...)
  body-of-labels)
```


### その他の特殊形式（Other Special Forms）

いくつかの特殊形式は、どの分類にもきれいに当てはまらない。
これまでに、定数や関数を生成する2つの特殊形式 `quote` と `function` を見てきた。
これらは非常に頻繁に使われるため、省略形が用意されている：
`'x` は `(quote x)` の略であり、`#'f` は `(function f)` の略である。

---

特殊形式 `progn` は、複数の式を順に評価し、最後の式の値を返すために使われる：

```lisp
(progn (setf x 0) (setf x (+ x 1)) x) => 1
```

`progn` は他の言語でいう `begin...end` ブロックに相当するが、Lisp では使用頻度は非常に低い。
その理由は2つある。

1. **関数型スタイルのプログラム**では副作用がないため、複数の操作を順に実行する必要がない。
2. **副作用を伴う場合**でも、多くの特殊形式が「本体（body）」として複数の式を受け入れる ― すなわち暗黙の `progn` を備えている。

`progn` を使うのが正当化される場面は、私の考えでは3つしかない。

---

**(1)** 2枝の条件文の中で副作用を実装したい場合、`if` と `progn` の組み合わせ、または `cond` が使える：

```lisp
(if (> x 100)
    (progn (print "too big")
           (setf x 100))
    x)

(cond ((> x 100)
       (print "too big")
       (setf x 100))
      (t x))
```

もし条件分岐が1つしかない場合は、`when` か `unless` を使うべきである。これらは暗黙の `progn` を持つ。
2つより多い分岐がある場合は `cond` を使う。

---

**(2)** `progn` は、複数のトップレベル形式に展開するマクロで必要になることがある。
例としては、p.326 の [§10.3](chapter10.md#s0020) にある `defun*` マクロがある。

---

**(3)** `unwind-protect`（高度なマクロ）の中で必要になる場合がある。
例としては、p.338 の [§10.4](chapter10.md#s0025) にある `with-resource` マクロが挙げられる。

---

`trace` と `untrace` の形式は、関数の呼び出しと終了に関するデバッグ情報を制御するために使われる：

```lisp
> (trace length9) => (LENGTH9)
> (length9 '(a b c)) =>
(1 ENTER LENGTH9: (A B C))
  (2 ENTER LENGTH9: (B C))
    (3 ENTER LENGTH9: (C))
      (4 ENTER LENGTH9: NIL)
      (4 EXIT LENGTH9: 0)
    (3 EXIT LENGTH9: 1)
  (2 EXIT LENGTH9: 2)
(1 EXIT LENGTH9: 3)
3

> (untrace length9) => (LENGTH9)
> (length9 '(a b c)) => 3
```

---

最後に、特殊形式 `return` は、コードブロックから途中で抜け出すために使われる。
ブロックは特殊形式 `block` によって、あるいはループ構文（`do`, `do*`, `dolist`, `dotimes`, `loop`）によって設定される。

次の関数は、数値リストの積を計算する。
ただし、もし途中に 0 があれば全体の積も 0 になるため、`dolist` ループの中で即座に 0 を返す。
この `RETURN` は関数全体ではなく、`dolist` のブロックからのみ抜け出すことに注意。
ただし、この場合 `dolist` が関数の最後の式であるため、`RETURN` の結果がそのまま関数の戻り値になる。
ここで `RETURN` を大文字にしているのは、「ループから脱出する」という異常な動作であることを強調するためである。

```lisp
(defun product (numbers)
  "Multiply all the numbers together to compute their product."
  (let ((prod 1))
    (dolist (n numbers prod)
      (if (= n 0)
          (RETURN 0)
          (setf prod (* n prod))))))
```

---

### マクロ（Macros）

ここまでの議論では、「特殊形式」という語をやや無造作に使ってきた。
実際のところ、これらのうちいくつかは **マクロ（macro）** ― つまりコンパイラが他のコードに展開する形式 ― である。

Common Lisp は多くの組み込みマクロを提供しており、ユーザも新しいマクロを定義して言語を拡張できる。
（ただし、ユーザが新しい「特殊形式」を定義することはできない。）

---

マクロは特殊形式 `defmacro` によって定義する。
たとえば Pascal の `while` ループ文のように動作するマクロ `while` を定義したいとしよう。
マクロを作るには次の4段階を踏む。

1. そのマクロが本当に必要かどうかを判断する。
2. マクロの構文を決める。
3. そのマクロがどんなコードに展開すべきかを考える。
4. `defmacro` を使って構文と展開の対応を実装する。

---

マクロを書くとき最初に意識すべきことは、**マクロを書くたびに Lisp に新しい言語要素を追加している**という点である。
そのことを自覚するプログラマは、マクロ定義に対して非常に慎重になるべきである。
（とはいえ、「今日何をしたの？」と聞かれて「新しい言語を定義してコンパイラを書いた」と言う方が、「マクロを2つ書いただけ」よりずっと格好いいのも確かだ。）

マクロを導入することは、関数や変数、データ型を導入するよりも読者に負担をかける。
したがって、軽い気持ちで定義してはいけない。
マクロは明確な必要性があり、既存のシステムと調和する場合にのみ導入すべきである。
C.A.R. Hoare の言葉を借りれば、

> 「言語設計者がやってはいけないことのひとつは、自分自身の未検証のアイデアを言語に取り込むことだ。」

---

次の段階は、マクロがどのようなコードに展開されるかを決めることだ。
マクロの構文は、可能な限り既存の Lisp の慣例に従うのが望ましい。
たとえば、ループ系のマクロ（`dolist`, `dotimes`, `do-symbols`）、
定義系のマクロ（`defun`, `defvar`, `defparameter`, `defstruct`）、
I/O 系のマクロ（`with-open-file`, `with-open-stream`, `with-input-from-string`）などが参考になる。

命名や構文の慣例を自分で発明するよりも、それらに倣う方がプログラムの読者にとって親切である。
`while` の場合、適切な構文は次のようなものである：

> `(while` *test body...*)

---

次に、マクロ呼び出しが展開されるべきコードを考える：

```lisp
(loop
  (unless test (return nil))
  body)
```

---

最後に、`defmacro` を使ってマクロ定義を書く。
`defmacro` の形式は `defun` に似ており、引数リスト、ドキュメンテーション文字列、本体を持つ。
ただし、引数リストで使える構文にいくつか違いがある（これについては後で説明する）。

以下は、テスト式と本体を取り、前述の `loop` コードを構築する `while` マクロの定義である。

```lisp
(defmacro while (test &rest body)
  "Repeat body while test is true."
  (list* 'loop
         (list 'unless test '(return nil))
         body))
```

（関数 `list*` は `list` に似ているが、最後の引数が他の引数リストの末尾に直接結合される点が異なる。）

---

`macroexpand` を使えば、このマクロがどのように展開されるか確認できる。
以下にその例を示す：

```lisp
> (macroexpand-1 '(while (< i 10)
                   (print (* i i))
                   (setf i (+ i 1)))) =>
(LOOP (UNLESS (< I 10) (RETURN NIL))
      (PRINT (* I I))
      (SETF I (+ I 1)))
> (setf i 7) => 7
> (while (< i 10)
    (print (* i i))
    (setf i (+ i 1)))
49
64
81
NIL
```

第24章 [§24.6](chapter24.md)（p.853）では、より複雑なマクロと、複雑なマクロを書く際の落とし穴（p.855）について説明している。

---

### バッククォート記法（Backquote Notation）

`while` を定義する際に最も難しい部分は、マクロ展開後のコードを構築する点である。
より直接的にコードを組み立てる方法があれば便利だ。
次のバージョンの `while` は、その試みである。

ここでは、ローカル変数 `code` にテンプレートとなるコードを定義し、
プレースホルダである `test` と `body` の箇所を、実際の値に置き換える。
この置換には関数 `subst` を使う。
（`subst new old tree` は、*tree* 内の *old* の出現箇所をすべて *new* に置き換える。）

```lisp
(defmacro while (test &rest body)
  "Repeat body while test is true."
  (let ((code '(loop (unless test (return nil)) . body)))
    (subst test 'test (subst body 'body code))))
```

---

このように、コード（や非コードのデータ）を部品から組み立てる場面は頻繁に現れるため、
Common Lisp ではそれを簡潔に表現するための特別な記法 ― **バッククォート（backquote）記法** ― が用意されている。

バッククォート文字 ``"`"`` は、引用符 `"'"` に似ているが、
「大部分はリテラルだが、一部には評価される部分を含む」ことを示す。

先頭にコンマ `,` が付いた部分は評価されて挿入される。
先頭にカンマ・アットマーク `,@` が付いた部分は、リストを展開（splice）して挿入される ―
つまり、そのリストの各要素がトップレベルの括弧なしで挿入される。

この記法については [§23.5](chapter23.md#s0030) で詳しく述べる。
ここでは、バッククォートとコンマを使って `while` を書き直してみよう：

```lisp
(defmacro while (test &rest body)
  "Repeat body while test is true."
  `(loop (unless ,test (return nil))
         ,@body))
```

---

以下にバッククォートの追加例を示す。
リストの末尾では、`",@"` は `"."` に続く `","` と同じ効果を持つ。
リストの途中では `",@"` のみが使用できる。

```lisp
> (setf test1 '(a test)) => (A TEST)

> `(this is ,test1) => (THIS IS (A TEST))

> `(this is ,@test1) => (THIS IS A TEST)

> `(this is . ,test1) => (THIS IS A TEST)

> `(this is ,@test1 -- this is only ,@test1) =>
(THIS IS A TEST -- THIS IS ONLY A TEST)
```

---

これで、特殊形式とマクロに関する節は完了である。
この章の残りの節では、Common Lisp における主要な組み込み関数の概要を解説する。

## 3.3 リストに対する関数（Functions on Lists）

以下のような代入が行われているものと仮定しよう：

```lisp
(setf x '(a b c))
(setf y '(1 2 3))
```

リストに対する最も重要な関数を以下にまとめる。
より複雑なものについては、この後で実際に使用される箇所で詳しく説明する。

| []()             |                        |                         |
| ---------------- | ---------------------- | ----------------------- |
| `(first x)`      | => `a`                 | リストの最初の要素               |
| `(second x)`     | => `b`                 | リストの2番目の要素              |
| `(third x)`      | => `c`                 | リストの3番目の要素              |
| `(nth 0 x)`      | => `a`                 | リストの n 番目の要素（0始まり）      |
| `(rest x)`       | => `(b c)`             | 最初の要素を除いた残り             |
| `(car x)`        | => `a`                 | リストの最初の要素（`first` の別名）  |
| `(cdr x)`        | => `(b c)`             | 最初の要素を除いた残り（`rest` の別名） |
| `(last x)`       | => `(c)`               | リストの最後の cons セル         |
| `(length x)`     | => `3`                 | リストの要素数                 |
| `(reverse x)`    | => `(c b a)`           | リストを逆順に並べ替える            |
| `(cons 0 y)`     | => `(0 1 2 3)`         | リストの先頭に要素を追加する          |
| `(append x y)`   | => `(a b c 1 2 3)`     | 要素を連結する                 |
| `(list x y)`     | => `((a b c) (1 2 3))` | 新しいリストを作成する             |
| `(list* 1 2 x)`  | => `(1 2 a b c)`       | 最後の引数を他の引数に連結する         |
| `(null nil)`     | => `T`                 | 空リストに対して真を返す述語          |
| `(null x)`       | => `nil`               | それ以外のものに対しては偽を返す        |
| `(listp x)`      | => `T`                 | `nil` を含む任意のリストに対して真    |
| `(listp 3)`      | => `nil`               | リストでないものに対しては偽          |
| `(consp x)`      | => `T`                 | `nil` でないリストに対して真       |
| `(consp nil)`    | => `nil`               | 原子（`nil` を含む）に対して偽      |
| `(equal x x)`    | => `T`                 | 同じ見た目のリストに対して真          |
| `(equal x y)`    | => `nil`               | 異なる見た目のリストに対して偽         |
| `(sort y #'>)`   | => `(3 2 1)`           | 比較関数に基づいてリストをソートする      |
| `(subseq x 1 2)` | => `(B)`               | 指定範囲の部分列を取り出す           |

---

これまで、`(cons a b)` は「要素 *a* をリスト *b* の先頭に追加してより長いリストを作る」と述べてきた。
では、*b* がリストでない場合はどうなるだろうか？

これはエラーにはならない。
結果として得られるオブジェクト *x* は次のような性質を持つ：

* `(first x)` => *a*
* `(rest x)` => *b*

そして *x* は `(*a* . *b*)` という形で出力される。
この表記法を **ドット対（dotted pair）** と呼ぶ。

*b* がリストである場合、出力時には通常のリスト表記が使われる（ドット対表記ではなく）。
しかし、どちらの表記法も入力として使用できる。

---

これまでリストを「3つの要素を持つリスト」といったように**シーケンス**として考えてきた。
しかし、実際の実装では、リストはより低レベルな構成要素である **consセル（cons cell）** に基づいている。

consセルは「最初の要素（first）」と「残り（rest）」の2つのフィールドを持つデータ構造である。

したがって、「3つの要素を持つリスト」は次のように見ることができる：

* 最初の cons セルが最初の要素を指し、
  その `rest` フィールドが「2要素からなるリストを表す cons セル」を指す。
* 2番目の cons セルは、さらに `rest` フィールドとして「3番目の要素を含む cons セル」を持つ。
* 最後の cons セルの `rest` フィールドは `nil` である。

すべての**正しいリスト（proper list）**は、末尾の cons セルの `rest` が `nil` で終わる。

## 3.4 等価性と内部表現（Equality and Internal Representation）

Lisp には主要な等価述語が 5 つ存在する。
なぜなら、すべてのオブジェクトが「同じように等しい（equally equal）」わけではないからである。

数値の等価述語 `=` は、2つの数が同じかどうかを判定する。
`=` を数値以外のオブジェクトに適用するのはエラーである。
その他の等価述語はどのようなオブジェクトにも適用できるが、
それらの違いを理解するには Lisp の内部動作について少し知る必要がある。

---

Lisp があるシンボルを2つの異なる場所で読み取った場合、
結果として得られるのは常に**同一のシンボル**であることが保証されている。
Lisp システムは **シンボルテーブル**を保持しており、関数 `read` は
文字列とシンボルの対応をこのテーブルで管理している。

しかし、リストを2つの異なる場所で読み込む（あるいは構築する）場合、
対応する要素が同じであっても、そのリスト自体は**同一のものではない**。
これは、`read` がリストを構築する際に `cons` を呼び出しており、
`cons` の呼び出しごとに新しい **cons セル** が作られるためである。

---

`x` の構造を共有していること、

数学的に等しい2つの数値が2つの場所で読み取られたり計算された場合、
それらが**同一のオブジェクトであるかどうか**は、
実装者がどちらをより効率的と判断したかによって異なる。

多くのシステムでは、等しい **fixnum（固定長整数）** 同士は同一 (`eq`) だが、
他の型（例えば float や bignum）では同一ではない。
（ただし short float では同一の場合もある。）

---

Common Lisp には、より一般的なものへと階層化された4種類の等価述語が用意されている。
これら4つはすべて `eq` で始まり、
名前が長くなるほど「より多くのオブジェクトを等しいとみなす」ようになる。

* 最も単純なのが **`eq`**：同一のオブジェクトであるかを判定する。
* **`eql`**：`eq` であるか、または等しい数値であるかを判定する。
* **`equal`**：`eql` であるか、または要素が `eql` なリストや文字列であるかを判定する。
* **`equalp`**：`equal` に似ているが、大文字・小文字を区別せず、型の異なる数値も等しいとみなす。

---

次の表は、さまざまな *x* と *y* の値に対して
それぞれの等価述語を適用したときの結果をまとめたものである。

`?` は実装依存を意味する：
2つの整数が `eql` であっても、`eq` であるとは限らない。

| *x*     | *y*     | `eq`  | `eql` | `equal` | `equalp` |
| ------- | ------- | ----- | ----- | ------- | -------- |
| `'X`    | `'x`    | `T`   | `T`   | `T`     | `T`      |
| `'0`    | `'0`    | `?`   | `T`   | `T`     | `T`      |
| `'(x)`  | `'(x)`  | `nil` | `nil` | `T`     | `T`      |
| `'"xy"` | `'"xy"` | `nil` | `nil` | `T`     | `T`      |
| `'"Xy"` | `'"xY"` | `nil` | `nil` | `nil`   | `T`      |
| `'0`    | `'0.0`  | `nil` | `nil` | `nil`   | `T`      |
| `'0`    | `'1`    | `nil` | `nil` | `nil`   | `nil`    |

---

さらに、次のような**特殊化された等価述語**も存在する：

* `=` — 数値を比較する
* `tree-equal` — 木構造を比較する
* `char-equal` — 文字を比較する
* `string-equal` — 文字列を比較する

これらはそれぞれ、対応する型（数値・ツリー・文字・文字列）専用の等価性を判定するために使われる。

## 3.5 シーケンスに対する関数（Functions on Sequences）

Common Lisp は、過去の Lisp と未来の Lisp の中間に位置する**過渡期の言語**である。
そのことが最もよく表れているのが、「シーケンス関数（sequence functions）」である。

---

初期の Lisp は **シンボル・数値・リスト** だけを扱い、
`append` や `length` のようなリスト操作関数のみを提供していた。
より新しい Lisp では、**ベクタ（vector）・文字列（string）・その他のデータ型** が導入され、
それらすべてをまとめて指す用語として **シーケンス（sequence）** が採用された。

（ベクタとは一次元の配列である。
`rest` ポインタを保持する必要がないため、リストよりも**コンパクトに表現**できる。
また、ポインタの鎖をたどる必要がないため、ベクタの *n* 番目の要素へのアクセスは**より効率的**である。）

さらに現代の Lisp では、**文字のベクタとしての文字列（string）**もサポートしており、
したがって文字列もシーケンスの一種（サブタイプ）である。

---

新しいデータ型が追加されると、それらを操作する関数の**命名の問題**が生じた。
Common Lisp は場合によって異なる方針を取っている。

* **古い関数を拡張する場合：**
  例）`length` はリストだけでなくベクタにも適用できる。

* **古い名前をリスト専用に残す場合：**
  新しい名前を汎用シーケンス関数に割り当てた。
  例）`append` と `mapcar` はリスト専用だが、
  `concatenate` と `map` は任意のシーケンスで動作する。

* **特定のデータ型専用に新関数を導入する場合：**
  たとえば、シーケンスの *n* 番目の要素を取り出す関数は **7種類** ある。

---

最も汎用的なのは `elt` で、どの種類のシーケンスにも使える。
しかし、リスト・配列・文字列・ビットベクタ・単純ビットベクタ・単純ベクタのそれぞれに専用の関数が存在する。
やや紛らわしいことに、**`nth` だけがインデックスを第1引数として取る**。

* `(nth` *n list*)
* `(elt` *sequence n*)
* `(aref` *array n*)
* `(char` *string n*)
* `(bit` *bit-vector n*)
* `(sbit` *simple-bit-vector n*)
* `(svref` *simple-vector n*)

---

この章の他の節では、それぞれの用途に応じて最も重要なシーケンス関数が紹介される。

## 3.6 テーブルを管理するための関数（Functions for Maintaining Tables）

Lisp のリストは、**一次元のオブジェクト列**を表すために使うことができる。
しかしその汎用性の高さゆえに、**情報のテーブル（表）**を表現する目的にも利用されてきた。

---

### アソシエーションリスト（association list）

**アソシエーションリスト（association list）**とは、
テーブルを実装するために使われるリストの一種である。
アソシエーションリストは **ドット対（dotted pair）** のリストであり、
各ペアは「キー（key）」と「値（value）」から構成される。

これらのペアをまとめたものがテーブルであり、
「キーを指定して対応する値を取得する」または
「そのキーが登録されていないことを確認する」ことができる。

---

次の例は、州の略称から州名を調べるものである。
このときに使う関数が `assoc` である。
`assoc` は、対応する **キーと値のペア**（あれば）を返す。
値だけを得たい場合は、返り値に対して `cdr` を取る。

```lisp
(setf state-table
  '((AL . Alabama) (AK . Alaska) (AZ . Arizona) (AR . Arkansas)))

> (assoc 'AK state-table) => (AK . ALASKA)

> (cdr (assoc 'AK state-table)) => ALASKA

> (assoc 'TX state-table) => NIL
```

---

キーではなく **値から検索**したい場合は、`rassoc` を使う。

```lisp
> (rassoc 'Arizona state-table) => (AZ . ARIZONA)
> (car (rassoc 'Arizona state-table)) => AZ
```

`assoc` によるテーブル管理は単純である。
ただし欠点がひとつある — **リスト全体を先頭から順に探索**しなければならない点だ。
リストが非常に長い場合、検索には時間がかかる。

---

### ハッシュテーブル（hash table）

もう1つの方法は **ハッシュテーブル（hash table）** を使うものである。
ハッシュテーブルは大量のデータを効率的に扱うよう設計されているが、
その分の**オーバーヘッド**があり、小規模なテーブルには向かない場合もある。

`gethash` 関数は `get` に似ており、2つの引数（キーとテーブル）を取る。
テーブルはまず `make-hash-table` で初期化し、
`gethash` に対する `setf` によって値を設定する。

```lisp
(setf table (make-hash-table))

(setf (gethash 'AL table) 'Alabama)
(setf (gethash 'AK table) 'Alaska)
(setf (gethash 'AZ table) 'Arizona)
(setf (gethash 'AR table) 'Arkansas)
```

テーブルから値を取得するには：

```lisp
> (gethash 'AK table) => ALASKA
> (gethash 'TX table) => NIL
```

`remhash` はキーと値のペアを削除し、
`clrhash` はすべてのペアを削除する。
`maphash` はキーと値のペアを順に処理するために使える。

ハッシュテーブルのキーは制限されておらず、**任意の Lisp オブジェクト**をキーにできる。
Common Lisp ではハッシュテーブルの実装に関してさらに多くの詳細があり、
その理論についても広範な文献が存在する。

---

### プロパティリスト（property list）

テーブルを表現する**第3の方法**は、**プロパティリスト（property list）**を使うものである。
プロパティリストは、**キーと値が交互に並んだリスト**である。

プロパティリスト（p-list または plist）と
アソシエーションリスト（a-list または alist）は似ている：

```
a-list: ((key₁ . val₁) (key₂ . val₂) ... (keyₙ . valₙ))
p-list: (key₁ val₁ key₂ val₂ ... keyₙ valₙ)
```

この表現の違いからわかるように、
a-list と p-list は情報の順序が少し異なるだけで、
基本的には同じ情報を持っている。

違いは「**通常どのように使われるか**」にある。

---

Lisp のすべてのシンボルには、それぞれ固有の**プロパティリスト**が関連付けられている。
つまり、シンボルに対して直接「プロパティと値のペア」を結びつけることができる。

ほとんどのプログラムでは、利用するプロパティの種類は少なく、
各プロパティに多数のシンボルが紐づく構造になる。
したがって、各シンボルのプロパティリストは短くなる傾向がある。

例として、各州の略称に対応する州名という**1種類のプロパティ**しか扱わない場合、
アソシエーションリストのように50個のペアをもつよりも、
シンボルごとに1つのプロパティをもつ形のほうがはるかに短くなる。

---

プロパティ値の取得には `get` 関数を使う。
`get` は2つの引数を取り、
第1引数は情報を取得したいシンボル、
第2引数はそのシンボルに紐づくプロパティの名前である。

`get` はそのプロパティに値があれば返す。
値の設定は `setf` によって行う。
テーブルを構築するには次のようにする：

```lisp
(setf (get 'AL 'state) 'Alabama)
(setf (get 'AK 'state) 'Alaska)
(setf (get 'AZ 'state) 'Arizona)
(setf (get 'AR 'state) 'Arkansas)
```

値を取得するには：

```lisp
> (get 'AK 'state) => ALASKA
> (get 'TX 'state) => NIL
```

---

この方法は、どれだけ多くのシンボルがプロパティを持っていても、
シンボルから直接そのプロパティ値にアクセスできるため**高速**である。
ただし、1つのシンボルが複数のプロパティを持つ場合は、
プロパティリスト内を**線形探索**する必要がある。

リンカーン風に言えば：
「テーブル検索の一部を速くすることはできるが、
すべてのテーブル検索を常に速くすることはできない。」

---

プロパティリストには `rassoc` に相当する関数が存在しない。
州名から略称を得たい場合には、
逆に「州」に対して「略称」というプロパティを設定する必要がある：

```lisp
(setf (get 'Arizona 'abbrev) 'AZ)
```

---

実際には、ソース・プロパティ・値のすべてがシンボルである場合、
プロパティの使い方にはいくつかのバリエーションがある。

たとえば、a-list 方式を模倣して
すべてのプロパティを1つのシンボルの下にまとめることもできる。
その場合、`symbol-plist`（シンボルのプロパティリスト全体を返す関数）に対して
`setf` を使う：

```lisp
(setf (symbol-plist 'state-table)
      '(AL Alabama AK Alaska AZ Arizona AR Arkansas))
> (get 'state-table 'AL) => ALASKA
> (get 'state-table 'Alaska) => NIL
```

---

プロパティリストは Lisp の長い歴史の中で使われてきたが、
**ハッシュテーブル**などの新しい手法の登場により、次第に使われなくなりつつある。
避けられる理由は主に2つある。

1. **グローバル性の問題**
   シンボルとそのプロパティリストはグローバルであるため、
   プロパティリストを使う2つのプログラムを組み合わせようとすると
   衝突が起こりやすい。
   同じプロパティ名を別の目的で使っている場合は共存できない。
   また、異なるプロパティを同じシンボルに付与していても
   お互いの処理を遅くする可能性がある。

2. **管理の煩雑さ**
   プロパティリストを使って作ったテーブルの全要素を
   一度に削除する簡単な方法が存在しない。
   これに対し、ハッシュテーブルでは `clrhash` で容易に消去でき、
   アソシエーションリストなら `nil` を代入するだけで済む。

## 3.7 木に対する関数（Functions on Trees）

多くの Common Lisp の関数は、式 `((a b) ((c)) (d e))` を「3つの要素からなるシーケンス」として扱う。
しかし、いくつかの関数はこれを「5つの非 `nil` の葉をもつ木構造」として扱う。

---

関数 `copy-tree` は木のコピーを作成し、
`tree-equal` は2つの木が等しいかどうかを、**cons セルをたどって**判定する。
ただし、ベクタや文字列のような他の複雑なデータ構造は対象外である。

この点で `tree-equal` は `equal` と似ているが、
`tree-equal` のほうが強力である。
なぜなら `:test` キーワードを指定できるからである。

```lisp
> (setf tree '((a b) ((c)) (d e)))

> (tree-equal tree (copy-tree tree)) => T

(defun same-shape-tree (a b)
  "葉の内容を除けば、2つの木の形が同じか？"
  (tree-equal a b :test #'true))

(defun true (&rest ignore) t)

> (same-shape-tree tree '((1 2) ((3)) (4 5))) => T
> (same-shape-tree tree '((1 2) (3) (4 5))) => NIL
```

---

また、木構造の中の任意の位置で、古い式を新しい式に**置き換える**ための関数が2つある。
`subst` は**1つの値**を別の値に置き換え、
`sublis` は**複数の置換**を行うためのもので、
置換リスト（アソシエーションリスト：(*old . new*) のペアのリスト）を取る。

注意すべき点は、`sublis` に渡すアソシエーションリスト内の「old と new の順序」が、
`subst` の引数順とは**逆**であることだ。

`sublis` という名前は Lisp にしては珍しく短く、やや分かりにくい。
より良い名前をつけるなら `subst-list` のほうが適切だろう。

```lisp
> (subst 'new 'old '(old ((very old)))) => (NEW ((VERY NEW)))

> (sublis '((old . new)) '(old ((very old)))) => (NEW ((VERY NEW)))

> (subst 'new 'old 'old) => NEW
```

---

次の例は、`sublis` を使って英語からフランス語への簡単な語句変換を行う関数である。

```lisp
(defun english->french (words)
  (sublis '((are . va) (book . libre) (friend . ami)
            (hello . bonjour) (how . comment) (my . mon)
            (red . rouge) (you . tu))
          words))

> (english->french '(hello my friend - how are you today?)) =>
(BONJOUR MON AMI - COMMENT VA TU TODAY?)
```

このように、`sublis` は木構造やリスト全体に対して、
単語やシンボルの置換を柔軟に行うことができる。

## 3.9 集合に対する関数（Functions on Sets）

リストの重要な用途のひとつは、**集合（set）**を表現することである。
Common Lisp には、リストを集合として扱うための関数がいくつか用意されている。

---

たとえば、集合
*r* = {*a, b, c, d*} と *s* = {*c, d, e*}
の間に共通する要素を求めたいとする。
その場合、次のようにできる：

```lisp
> (setf r '(a b c d)) => (A B C D)
> (setf s '(c d e)) => (C D E)
> (intersection r s) => (C D)
```

この実装では答えとして `(C D)` が返されているが、
別の実装では `(D C)` を返すこともある。
どちらも等価な集合であるため、どちらの結果も正しい。
したがって、**結果の要素順序に依存するプログラムを書いてはいけない。**

---

主な集合操作関数を以下に示す：

| 式                      | 結果               | 説明                         |
| ---------------------- | ---------------- | -------------------------- |
| `(intersection r s)`   | => `(c d)`       | 2つの集合の共通部分を求める             |
| `(union r s)`          | => `(a b c d e)` | 2つの集合の和集合（いずれかに含まれるすべての要素） |
| `(set-difference r s)` | => `(a b)`       | 一方にのみ含まれる要素（差集合）           |
| `(member 'd r)`        | => `(d)`         | 要素が集合に含まれているかを調べる          |
| `(subsetp s r)`        | => `nil`         | ある集合が別の集合の部分集合かを調べる        |
| `(adjoin 'b s)`        | => `(b c d e)`   | 要素を集合に追加する                 |
| `(adjoin 'c s)`        | => `(c d e)`     | ただし重複要素は追加しない              |

---

### ビット列による集合表現

特定の「全体集合（universe of discourse）」が与えられている場合、
集合をビット列で表すこともできる。

たとえば、全体集合が (`a b c d e`) であるとすると：

* (`a b c d`) はビット列 **11110**
* 空集合は **00000**
* (`a b e`) は **11001**

で表現できる。

このビット列は Common Lisp では次の2通りで表現できる：

* **ビットベクタ（bit vector）**： `#*11001`
* **2進整数（binary integer）**： `#b11001`（＝ 25）

---

### ビット表現の利点

ビット列を使う利点は、
全体集合が小さい場合に**集合の表現が省メモリで済む**こと、
そして**計算が高速**であることだ。

なぜなら、CPU の命令セットは通常、
32個のビット（＝32要素）を一度に処理できるからである。

---

### 対応する関数群

Common Lisp では、ビットベクタおよび整数の両方に対して
完全な集合演算関数群が用意されている。
次の表は、リストに対する関数と、それに対応する整数・ビットベクタ関数を示している。

| リスト関数            | 整数関数       | ビットベクタ関数    |
| ---------------- | ---------- | ----------- |
| `intersection`   | `logand`   | `bit-and`   |
| `union`          | `logior`   | `bit-ior`   |
| `set-difference` | `logandc2` | `bit-andc2` |
| `member`         | `logbitp`  | `bit`       |
| `length`         | `logcount` | （該当なし）      |

---

### 例

```lisp
(intersection '(a b c d) '(a b e)) =>  (A B)
(bit-and      #*11110    #*11001)  =>  #*11000
(logand       #b11110    #b11001)  =>  24 = #b11000
```

このように、リスト演算とビット演算は対応しており、
同じ集合演算を異なる表現形式で効率的に行うことができる。

## 3.10 破壊的関数（Destructive Functions）

数学において、**関数（function）**とは、いくつかの入力引数を与えられたときに出力値を計算するものである。
関数は「何かを行う（do）」ものではなく、**単に結果を計算する**ものである。

たとえば、もし私が「*x* = 4 および *y* = 5」とあなたに伝え、関数「plus」を *x* と *y* に適用してほしいと言ったなら、
あなたは当然「9」と答えるだろう。
その後で「では、*x* の値はいくつか？」と聞かれたとき、
もし *x* の値が変わっていたとしたら、それは奇妙に感じるはずである。
数学では、演算子を *x* に適用しても *x* の値には何の影響も与えない。

---

しかし Lisp では、**単に結果を計算するだけでなく副作用を及ぼす関数**も存在する。 <a id="tfn03-2"></a>
このような「関数」は、数学的な意味での関数ではなく、
他の言語では「**手続き（procedure）**」と呼ばれるものである。

もちろん、Lisp のほとんどの関数は純粋な数学的関数である。
だが、そうでないごく一部の関数は、**大きな問題を引き起こす可能性**もあれば、
**特定の状況では非常に有用**でもある。
その両方の理由から、これらの関数を知っておく価値がある。

---

次の例を考えてみよう：

```lisp
> (setf x '(a b c)) => (A B C)
> (setf y '(1 2 3)) => (1 2 3)
> (append x y) => (A B C 1 2 3)
```

`append` は**純粋関数（pure function）**である。
したがって、`append` の呼び出しを評価した後でも、
`x` と `y` の値は変化していないことが期待できる。

---

では、次の例を見てみよう：

```lisp
> (nconc x y) => (A B C 1 2 3)
> x => (A B C 1 2 3)
> y => (1 2 3)
```

関数 `nconc` は `append` と同じ結果を計算するが、
**最初の引数を変更する副作用を持つ**。

このような関数は、既存の構造を**破壊して置き換える**ため、
「**破壊的関数（destructive function）**」と呼ばれる。

`nconc` を使用するプログラマは、
最初の引数が変更される可能性を理解し、
それを踏まえて設計する必要がある。
これは、純粋関数のように「結果だけを考えればよい」場合よりも、
はるかに複雑で注意を要する。

---

### `nconc` の利点と注意点

`nconc` の利点は、**追加のメモリを消費しない**ことである。
`append` は `x` の完全なコピーを作成し、その末尾を `y` に接続する必要があるが、
`nconc` はコピーを作成せず、
単に `x` の最後の要素の「rest フィールド」を `y` に**書き換える**だけである。

したがって、**メモリ節約が必要な場合**には破壊的関数を使う価値があるが、
**その影響を十分に理解した上で使わなければならない**。

---

`nconc` のほかにも、多くの破壊的関数の名前は `n` から始まる。
例として以下のものがある：

* `nreverse`
* `nintersection`
* `nunion`
* `nset-difference`
* `nsubst`

重要な例外として、`remove` の破壊的版である `delete` がある。

もちろん、`setf` 特殊形式を使って構造を変更することも可能だが、
特に**破壊的関数のほうが危険**である。
なぜなら、その影響を**見落としやすい**からである。

---

ユーザーは何らかのものを心に思い浮かべ、

## 3.11 データ型の概要（Overview of Data Types）

この章ではこれまで、関数を中心に構成されてきた。
似たような関数をグループ化して説明してきたが、Common Lisp の世界をもう一つの観点から整理する方法がある。
それは、**異なるデータ型（data types）**に着目する方法である。

これは次の2つの理由で有用である。

1. 利用可能な機能の多様性を、別の角度から理解できる。
2. データ型そのものも Common Lisp のオブジェクトであり、後述するように、データ型を操作する関数が存在する。

これらの関数は主に、**オブジェクトの型を判定する（例：`typecase` マクロで）**、あるいは**宣言を行う**ために用いられる。

---

### 主なデータ型一覧

| 型名 (Type)    | 例 (Example)    | 説明 (Explanation)                          |
| ------------ | -------------- | ----------------------------------------- |
| `character`  | `#\c`          | 1文字（アルファベット・数字・句読点など）                     |
| `number`     | `42`           | 最も一般的な数値型。浮動小数点数（float）および整数（integer）を含む。 |
| `float`      | `3.14159`      | 小数点を含む数値。                                 |
| `integer`    | `42`           | 整数。固定長または任意長で表現される。                       |
| `fixnum`     | `123`          | 単一ワードに収まる整数。                              |
| `bignum`     | `123456789`    | サイズ制限のない大きな整数。                            |
| `function`   | `#'sin`        | 関数。引数リストに適用可能。                            |
| `symbol`     | `sin`          | シンボル。関数や変数の名前になり、またオブジェクトそのものでもある。        |
| `null`       | `nil`          | `nil` オブジェクトは null 型の唯一の要素。               |
| `keyword`    | `:key`         | キーワード。symbol 型のサブタイプ。                     |
| `sequence`   | `(a b c)`      | シーケンス。list と vector を含む。                  |
| `list`       | `(a b c)`      | リスト。`cons` か `null` のいずれか。                |
| `vector`     | `#(a b c)`     | ベクタ。sequence のサブタイプ。                      |
| `cons`       | `(a b c)`      | 非 nil のリスト。                               |
| `atom`       | `t`            | cons 以外の任意のもの。                            |
| `string`     | `"abc"`        | 文字のベクタ型。                                  |
| `array`      | `#lA(a b c)`   | 配列。vector や多次元配列を含む。                      |
| `structure`  | `#S(type ...)` | `defstruct` により定義された構造体。                  |
| `hash-table` | ...            | `make-hash-table` により生成されるハッシュテーブル。       |

---

### 型認識関数（Recognizer Predicates）

ほぼすべてのデータ型には、**型認識述語（recognizer predicate）**と呼ばれる関数が存在する。
これは「その型の要素である場合にのみ真を返す」関数である。

一般に述語（predicate）は、常に **真または偽のいずれか**を返す関数である。
Lisp では、偽の値は `nil` であり、
それ以外のすべての値は真とみなされる（最も一般的な真の値は `t`）。

ほとんどの場合、認識述語の名前は「型名＋`p`」で構成される。
たとえば：

* `characterp` — 文字かどうかを判定
* `numberp` — 数値かどうかを判定

```lisp
(numberp 3)   => T
(numberp "x") => NIL
```

最初の呼び出しは `3` が数値であるため真を返すが、
後者は `"x"` が文字列であり数値ではないため偽を返す。

---

### 不規則性と例外

残念ながら、Common Lisp の体系は完全に規則的ではない。

* `fixnum`、`bignum`、`sequence`、`structure` には認識関数が存在しない。
* `null` と `atom` は例外的に `p` で終わらない。
* `hash-table-p` のように、型名にハイフンが含まれている場合、述語名にもハイフンが含まれる。
* また、`defstruct` により生成されるすべての認識関数も `-p` で終わる。

---

### 型操作関数

* `type-of` — 引数の型を返す
* `typep` — オブジェクトが特定の型かどうかを判定する
* `subtypep` — 一方の型が他方のサブタイプかどうかを判定する

例：

```lisp
> (type-of 123) => FIXNUM
> (typep 123 'fixnum) => T
> (typep 123 'number) => T
> (typep 123 'integer) => T
> (typep 123.0 'integer) => NIL
> (subtypep 'fixnum 'number) => T
```

---

### 型階層（Type Hierarchy）

Common Lisp の型階層は非常に複雑である。
上の例からもわかるように、数値には多くの型があり、
`123` は `fixnum` であり、`integer` であり、`number` でもある。
さらに、後に説明するように `rational` 型および `t` 型でもある。

型階層は単なる木構造ではなく、**グラフ構造**を形成している。
たとえば：

* `vector` は `sequence` と `array` の両方のサブタイプである。
  ただし `array` と `sequence` は互いにサブタイプ関係にない。
* `null` は `symbol` と `list` の両方のサブタイプである。

---

### より専門的なデータ型

次の表は、あまり頻繁には使われないが存在するデータ型を示している。

| 型名             | 例                     | 説明                         |
| -------------- | --------------------- | -------------------------- |
| `t`            | `42`                  | すべてのオブジェクトは型 `t` に属する。     |
| `nil`          | （なし）                  | 型 `nil` に属するオブジェクトは存在しない。  |
| `complex`      | `#C(0 1)`             | 複素数（imaginary number）。     |
| `bit`          | `0`                   | 0 または 1。                   |
| `rational`     | `2/3`                 | 有理数。整数と分数を含む。              |
| `ratio`        | `2/3`                 | 正確な分数。                     |
| `simple-array` | `#lA(x y)`            | 変形不可・非再配置の配列。              |
| `readtable`    | ...                   | 文字とその意味の対応表。               |
| `package`      | ...                   | シンボルの集合（モジュールを構成）。         |
| `pathname`     | `#P"/usr/spool/mail"` | ファイルまたはディレクトリ名。            |
| `stream`       | ...                   | オープンされたファイルへのポインタ（入出力に使用）。 |
| `random-state` | ...                   | `random` 関数が利用する乱数生成の内部状態。 |

---

さらに、次のようなより特殊な型も存在する：

* `short-float`
* `compiled-function`
* `bit-vector`

また、型をより正確に指定することも可能である。
たとえば：

```lisp
(vector (integer 0 3) 100)
```

これは「**100個の要素を持ち、それぞれの要素が 0〜3 の整数であるベクタ**」を表す。

型とその利用法については、[第10.1節](chapter10.md#s0010) に詳しく述べられている。

---

### 型以外の述語

ほとんどの型には述語関数が存在するが、
中には型を認識するのではなく、より一般的な条件を判定するものもある。

たとえば：

* `oddp` — 奇数の場合に真を返す。
* `string-greaterp` — 文字列が他の文字列よりアルファベット順で大きい場合に真を返す。


## 3.12 入出力（Input/Output）

Lisp における入力は驚くほど簡単である。
なぜなら、**完全な字句解析（lexical parsing）および構文解析（syntactic parsing）機構**がユーザに提供されているからである。

このパーサは `read` と呼ばれる。
`read` は **1つの Lisp 式を読み取り、それを返す** 関数である。
もしあなたのアプリケーションが Lisp 式を入力として受け取るように設計できるなら、入力処理に関する心配はほぼなくなるだろう。

---

### `read` の基本的な特徴

`read` が解析する式は、必ずしも **評価可能な（evaluable）Lisp 式**である必要はない。
たとえば次の2つの入力はいずれも読み取ることができる：

* `("hello" cons zzz)`
* `(+ 2 2)`

後者は評価可能だが、前者はそうではない。

Lisp 式が不適切な場合には、次のような低レベルの関数を使うことができる：

* `read-char` — **1文字を読み取る**
* `read-line` — **改行までの全入力を文字列として読み取る**

---

### 端末およびファイルからの入力

引数を与えずに呼び出すと：

* `read` は Lisp 式を返す
* `read-char` は1文字を返す
* `read-line` は行末までの文字列を返す

ファイルから読み取ることもできる。
そのためには、関数 `open` またはマクロ `with-open-stream` を用いてファイルを開き、
入力／出力の対象を表す **ストリーム（stream）** に関連付ける。

3つの読み取り関数はいずれも、**3つの省略可能な引数**を取る：

1. 読み取るストリーム
2. EOF（ファイルの終端）でエラーを起こすかどうか（true ならエラーを発生）
3. EOF 時に返す値（2番目が `nil` のときに有効）

---

### 出力（Output）

Lisp の出力は、Cなどの他の言語とよく似ている。
低レベルの出力関数がいくつか存在し、また**整形出力（formatted output）**のための強力な関数もある。

* `print` — オブジェクトを**改行付き**で表示し、末尾に空白を加える。
* `prin1` — 改行も空白も付けずにオブジェクトを表示する。
* `princ` — **人間に読みやすい形式**で表示する（引用符は付けない）。

`print` と `prin1` は、**`read` が再び読み取れる形式**で出力する。
たとえば文字列 `"hello there"` は `"hello there"` と表示される。
一方で `princ` は `"hello there"` を **hello there** と表示する（引用符は出力されない）。
したがって、この場合 `read` で再び元の形を正確に再現することはできない。

さらに、`write` 関数は **11個のキーワード引数**を取り、
`prin1` や `princ` のような挙動を細かく制御できる。

---

### ストリーム出力の例

出力関数もまた、**ストリームをオプション引数として指定**できる。
次の例では、`test.text` というファイルを作成し、そこに2つの式を書き出している。
その後、ファイルを読み取りモードで開き、順に読み戻す：

```lisp
> (with-open-file (stream "test.text" :direction :output)
    (print '(hello there) stream)
    (princ 'goodbye stream)) =>
GOODBYE        ; ファイル test.text が作成される

> (with-open-file (stream "test.text" :direction :input)
    (list (read stream) (read-char stream) (read stream)
          (read stream nil 'eof))) =>
((HELLO THERE) #\G OODBYE EOF)
```

ここで `read-char` は文字 `#\G` を返す。
その結果、次の `read` は `OODBYE` を読み取り、それを1つのシンボルに変換する。
最後の `read` は EOF に達し、指定した値 `eof` を返す。

---

### 改行制御関数

* `terpri` — 「terminate print line（出力行を終了）」の略。強制的に次の行へ移動する。
* `fresh-line` — 現在すでに行頭にある場合は改行せず、そうでない場合のみ改行する。

---

### 整形出力：`format` 関数

Common Lisp には非常に汎用的な整形出力関数 `format` が用意されている。

* 第1引数：出力先ストリーム。`t` を指定するとターミナルに出力。
* 第2引数：**フォーマット文字列（format string）**。

フォーマット文字列は基本的にそのまま出力されるが、
`"~"` で始まる **フォーマット指示子（format directive）** が含まれている場合、
その指示に従って引数が整形される。

この考え方は、C の `printf` や FORTRAN の `FORMAT` 文と似ている。

#### 例：

```lisp
> (format t "hello, world")
hello, world
NIL
```

---

### 引数付きの例

```lisp
> (format t "~&~a plus ~s is ~f" "two" "two" 4)
two plus "two" is 4.0
NIL
```

ここで：

* `~&` — 改行（新しい行へ）
* `~a` — 次の引数を `princ` の形式で出力
* `~s` — 次の引数を `prin1` の形式で出力
* `~f` — 数値を浮動小数点形式で出力（非数値なら `princ` を使用）

`format` 自体の戻り値は常に `nil` である。
フォーマット指示子は全部で **26種類**ある。

---

### 複雑な例

```lisp
> (let ((numbers '(1 2 3 4 5)))
    (format t "~&~{~r~^ plus ~} is ~@r"
            numbers (apply #'+ numbers)))
one plus two plus three plus four plus five is XV
NIL
```

* `~r` — 数値を英単語で出力（例：`3` → `three`）
* `~@r` — 数値をローマ数字で出力（例：`15` → `XV`）
* `~{ ... ~}` — 次の引数（リスト）を受け取り、
  内部のフォーマット指定に従って各要素を整形
* `~^` — 引数が尽きたら `~{...~}` ループを終了

---

このように、`format` は `loop` と同様に、
**ほとんど1つのプログラミング言語に匹敵するほど強力な仕組み**を持つ。
そして同様に、**Lisp らしからぬ構文的な言語**でもある。


## 3.13 デバッグツール（Debugging Tools）

多くのプログラミング言語には、デバッグのために次の2つの戦略がある：

1. **プログラムを編集して print 文を挿入し、再コンパイルして再実行する。**
2. **デバッガプログラムを使って、実行中のプログラムの内部状態を調査（場合によっては変更）する。**

Common Lisp はこれら2つの方法の両方をサポートしている。
しかしそれに加えて、第3の方法も提供している：

3. **プログラム本体とは独立した「注釈（annotation）」を追加し、それによって実行中のプログラムを自動的に変更する。**

この第3の戦略の利点は、デバッグが終わったあとに、
最初の方法で挿入した print 文などを**削除して元に戻す必要がない**ことである。

さらに Common Lisp には、プログラムの状態に関する情報を表示する関数も備わっている。
ソースコードだけを見て判断する必要はない。

---

### `trace` と `step`

すでに（65ページで）`trace` と `untrace` によって
デバッグ情報を得る方法を見てきた。

もう1つの便利なツールが `step` である。
これは、**各サブフォームを評価する前に実行を一時停止**するために使われる。

フォーム：

```lisp
(step <expression>)
```

は `<expression>` を評価してその結果を返すが、
その途中で一時停止し、ユーザが計算の様子を観察したり、
必要であれば途中で値を変更したりできる。

利用できるコマンドは実装依存であるが、
一般的に `?` を入力すれば利用可能なコマンド一覧が表示される。

以下の例では、同じ式を2回ステップ実行している。
最初の回はすべてのサブ評価で停止し、
2回目は関数呼び出し単位でスキップして実行している。

この実装ではコマンドが制御文字（control characters）で入力されるため、
出力には表示されていない。

---

以下の出力（記号 `<=` と `=>` を含む）はすべて stepper 自身によって生成されたものであり、
追加の注釈は一切ない。

```lisp
> (step (+ 3 4 (* 5 6 (/ 7 8))))
<= (+ 3 4 (* 5 6 (/ 7 8)))
  <= 3 => 3
  <= 4 => 4
  <= (* 5 6 (/ 7 8))
  <= 5 => 5
  <= 6 => 6
  <= (/ 7 8)
    <= 7 => 7
  <= 8 => 8
    <=(/ 7 8) => 7/8
  <= (* 5 6 (/ 7 8)) => 105/4
  <= (+ 3 4 (* 5 6 (/ 7 8))) => 133/4
133/4

> (step (+ 3 4 (* 5 6 (/ 7 8))))
<= (+ 3 4 (* 5 6 (/ 7 8)))
  /: 7 8 => 7/8
  *: 5 6 7/8 => 105/4
  +: 3 4 105/4 => 133/4
<= (+ 3 4 (* 5 6 (/ 7 8))) => 133/4
133/4
```

---

### プログラム情報の表示関数

関数 `describe`, `inspect`, `documentation`, `apropos` は、
現在のプログラムの状態に関する情報を提供する。

#### `apropos`

シンボル名が引数と一致するすべてのシンボルについて情報を表示する：

```lisp
> (apropos 'string)

PRIN1-TO-STRING        function (OBJECT)
PRINC-TO-STRING        function (OBJECT)
STRING                 function (X)
...
```

---

#### `describe`

興味のあるオブジェクトがわかったら、
`describe` を使ってより詳細な情報を得ることができる：

```lisp

```

---

#### `documentation`

単にシンボルのドキュメント文字列だけが必要な場合には、
`documentation` 関数を使用する：

```lisp

> (documentation 'pi 'variable) => "pi"
```

---

#### `inspect`

複雑な構造体の構成要素を**調べたり、変更したり**したい場合には `inspect` を使用する。
実装によっては、ウィンドウベースのブラウザのようなインターフェイスが起動されることもある。

---

### デバッガ

Common Lisp には、**エラーがシグナルされた際に自動的に起動されるデバッガ**も用意されている。
これはプログラムの誤りや、意図的に呼び出した場合（例えば `break` など）にも発生する。

デバッガの詳細は実装ごとに異なるが、標準的な起動方法がいくつか存在する。

---

#### `break`

`break` 関数は、**任意のメッセージを表示した後、デバッガに入る**。
主にブレークポイントを設定する目的で使用される。

```lisp
(break "Reached here with value ~A" x)
```

`break` はデバッグ専用であり、
プログラムが完成した段階ではすべて削除するのが望ましい。

ただし、異常状態を検出するためには、次のような関数を使用するのが良い：

* `error`
* `cerror`
* `assert`
* `check-type`

これらについては、次の節で説明する。

## 3.14 アンチバグツール（Antibugging Tools）

通常のデバッグに加えて、**アンチバグ（antibugging）チェック**をコードに組み込むのは良い考えである。
アンチバグコードとは、**エラーを検出し、必要であれば修正を試みる処理**を行うコードのことである。

---

### `error` と `cerror`

関数 `error` と `cerror` は、**エラー状態（error condition）を通知（signal）する**ために使われる。
これらの呼び出しは、プログラムのデバッグが完了した後もそのまま残しておくことを意図している。

`error` はフォーマット文字列と任意の引数を取り、**致命的エラー（fatal error）**を発生させる。
つまり、プログラムを停止し、再開の手段をユーザに提供しない。

例：

```lisp
(defun average (numbers)
  (if (null numbers)
      (error "Average of the empty list is undefined.")
      (/ (reduce #'+ numbers)
         (length numbers))))
```

---

多くの場合、致命的エラーはやや過剰である。
そのため、**継続可能なエラー（continuable error）**を発生させる `cerror` が用意されている。

`cerror` は2つのフォーマット文字列を受け取る：

1. 「継続した場合にどうなるか」を説明するメッセージ
2. エラーメッセージそのもの

`cerror` は実際にエラーを修復するわけではなく、
**ユーザが「続行してよい」と判断するための選択肢を提示する**だけである。

以下の実装では、`:continue` と入力することで継続できる。
ANSI Common Lisp では、継続オプションを指定するより洗練された方法もある。

```lisp
(defun average (numbers)
  (if (null numbers)
      (progn
        (cerror "Use 0 as the average."
                "Average of the empty list is undefined.")
        0)
      (/ (reduce #'+ numbers)
         (length numbers))))

> (average '())
Error: Average of the empty list is undefined.
Error signaled by function AVERAGE.
If continued: Use 0 as the average.
>> :continue
0
```

---

この例では、エラーチェックを追加した結果、
コードの長さがおよそ2倍になっている。

これは珍しいことではない。
**「想定通りの入力に対して動作するコード」**と
**「あらゆるエラー条件を網羅するコード」**の間には大きな差がある。

Common Lisp は、次のような特殊フォームを提供することで、
エラーチェックをより簡単に記述できるようにしている。

---

### `ecase` と `ccase`

* `ecase`（"exhaustive case" または "error case" の略）
  通常の `case` と似ているが、**どのケースにも一致しなかった場合にエラーを発生させる。**

* `ccase`（"continuable case" の略）
  `ecase` と似ているが、エラーが継続可能である。
  システムはユーザに新しい値の入力を求め、
  その値がどれかのケースに一致するまで再試行する。

---

### `check-type` と `assert`

Common Lisp はさらに、コードの肥大化を抑えながらエラーチェックを行うために
`check-type` と `assert` という2つの特殊フォームを提供している。

---

#### `check-type`

その名の通り、**引数の型を検査する**。
引数が誤った型の場合、継続可能なエラーを通知する。

例：

```lisp
(defun sqr (x)
  "Multiply x by itself."
  (check-type x number)
  (* x x))
```

もし非数値を渡すと、以下のようなメッセージが表示される：

```lisp
> (sqr "hello")
Error: the argument X was "hello", which is not a NUMBER.
If continued: replace X with new value
>> :continue 4
16
```

---

#### `assert`

`assert` は `check-type` よりも一般的なフォームである。
最も単純な形では、式をテストし、その結果が偽であればエラーを通知する。

```lisp
(defun sqr (x)
  "Multiply x by itself."
  (assert (numberp x))
  (* x x))
```

この場合、継続はできない。

`assert` は、指定した「修正可能な場所（place）」を変更して
式を真にすることを試みることもできる。

例：

```lisp
(defun sqr (x)
  "Multiply x by itself."
  (assert (numberp x) (x))
  (* x x))
```

アサーションが失敗すると、エラーメッセージが表示され、
ユーザは `x` の値を変更して続行できる。
もし新しい値が条件を満たせば、プログラムはそのまま続行される。
`assert` 自体は常に `nil` を返す。

---

#### `assert` の完全構文

`assert` にフォーマット文字列と引数を与えることで、
エラーメッセージをより詳細に制御できる。

完全な構文は次の通り：

> `(assert` *test-form* (*place...*) *format-ctl-string format-arg...*)

---

#### 例：クマの粥（porridge）の温度チェック

```lisp
(defun eat-porridge (bear)
  (assert (< too-cold (temperature (bear-porridge bear)) too-hot)
          (bear (bear-porridge bear))
          "~a's porridge is not just right: ~a"
          bear (hotness (bear-porridge bear)))
  (eat (bear-porridge bear)))
```

このアサーションは、「クマの粥の温度が熱すぎず冷たすぎない」ことを確認する。

以下のインタラクションでは、アサーションが失敗し、
プログラマのエラーメッセージと、2つの継続オプションが表示された。
ユーザはそのうち1つを選択し、新しい値として `make-porridge` を呼び出した結果、
プログラムは正常に続行した。

```lisp
> (eat-porridge momma-bear)
Error: #<MOMMA BEAR>'s porridge is not just right: 39
Restart actions (select using :continue):
 0: Supply a new value for BEAR
 1: Supply a new value for (BEAR-PORRIDGE BEAR)
>> :continue 1
Form to evaluate and use to replace (BEAR-PORRIDGE BEAR):
(make-porridge :temperature just-right)
nil
```

---

### アサーションを書く意味

アサーションが正常に動作すれば「使われない」かもしれない。
しかし、**完璧なプログラマを除けば、バグは必ず起こる。**
アンチバグコードにかけた時間は、後のデバッグ時間を大きく節約してくれる。

---

### 一貫性チェッカ（Consistency Checker）

複雑なデータ構造（例：データベースなど）を開発する際には、
**対応する一貫性チェッカ（consistency checker）**を作るのが良い。

この関数はデータ構造全体を調べ、
考えられるすべてのエラーをチェックする。
新たなエラーが見つかった場合、その検査をチェッカに追加していく。

こうしたチェッカを呼び出すことで、
構造的なバグを素早く特定できる。

---

### 回帰テスト（Regression Testing）

困難なテストケースの一覧を常に手元に残しておくのもよい。
プログラムを変更したとき、
過去に修正したバグが**再発していないか**を簡単に確認できるからである。

これを**回帰テスト（regression testing）**と呼ぶ。

Waters (1991) は、回帰テストのスイートを管理する興味深いツールを紹介しているが、
簡単な例なら以下のように `assert` を使って自作できる：

```lisp
(defun test-ex ()
  "Test the program EX on a series of examples."
  (init-ex) ; Initialize the EX program first.
  (assert (equal (ex 3 4) 5))
  (assert (equal (ex 5 0) 0))
  (assert (equal (ex 'x 0) 0)))
```

---

### タイミングツール（Timing Tools）

プログラムは「正しい出力を返す」だけでは完成ではない。
**結果を適切な速度で返すこと**も重要である。

フォーム：

```lisp
(time <expression>)
```

を使うと、指定した式の実行時間を計測できる。
実装によっては、メモリ使用量などの統計も表示される。

例：

```lisp
> (defun f (n) (dotimes (i n) nil)) => F
> (time (f 10000)) => NIL
Evaluation of (F 10000) took 4.347272 Seconds of elapsed time, including 0.0 seconds of paging time for 0 faults, Consed 27 words.

> (compile 'f) => F

> (time (f 10000)) => NIL
Evaluation of (F 10000) took 0.011518 Seconds of elapsed time, including 0.0 seconds of paging time for 0 faults, Consed 0 words.
```

この結果、**コンパイル版は300倍以上高速**であり、
しかもメモリ消費も少ないことがわかる。

多くの Common Lisp プログラマは、通常コンパイル済み関数のみを使用する。

しかし、プログラム開発初期段階で効率を気にしすぎるのは良くない。
まずは**柔軟な設計で動くものを作り、**
その後で**頻繁に使われる部分のみ最適化する**のが望ましい。

すなわち：

> 「開発段階」と「微調整段階」を分離せよ」

効率化に関する詳細は [第9章](chapter9.md) と [第10章](chapter10.md) に、
またデバッグとアンチバグ技術に関する追加の助言は [第25章](chapter25.md) に記されている。

## 3.15 評価（Evaluation）

Lisp には評価を行うための関数が3つある：
`funcall`, `apply`, そして `eval` である。

* `funcall` は、**関数を個々の引数に適用する**ために使われる。
* `apply` は、**関数を引数のリストに適用する**ために使われる。

実際には、`apply` に対しては最後の引数がリストであれば、
その前に1つまたはいくつかの個別の引数を与えることもできる。

一方、`eval` は1つの引数を取り、それは**完全なフォーム（form）**でなければならない。
つまり、関数または特殊形式とその引数からなる形、あるいは単なるアトム（atom）である。

次の5つのフォームはいずれも同じ結果を返す：

```lisp
> (+ 1 2 3 4)             => 10
> (funcall #'+ 1 2 3 4)   => 10
> (apply #'+ '(1 2 3 4))  => 10
> (apply #'+ 1 2 '(3 4))  => 10
> (eval '(+ 1 2 3 4))     => 10
```

---

過去には、`eval` は Lisp の柔軟性を支える中核的な仕組みとみなされていた。
しかし、**Common Lisp のようなレキシカルスコープ（lexical scoping）を持つモダンな Lisp** では、`eval` はそれほど頻繁には使われない。
（実際、Scheme には `eval` がまったく存在しない。）

現代の Lisp では、プログラマは `lambda` を用いて新しい関数を作り、
その関数を `apply` または `funcall` で呼び出すことが推奨される。

一般的に言えば、もしあなたが `eval` を使っているなら、
**たいていの場合それは誤ったアプローチ**である。

---

## 3.16 クロージャ（Closures）

「新しい関数を作る」とはどういう意味だろうか？
確かに、`function`（あるいは `#'`）の特殊形式を評価するたびに、
関数が返される。

しかし、これまでの例、そして次の例を見ても分かるように、
それは常に**同じ関数**が返されている。

```lisp
> (mapcar #'(lambda (x) (+ x x)) '(1 3 10)) => (2 6 20)
```

この `#'(lambda ...)` フォームを評価するたびに、
引数を2倍にする同じ関数が返される。

---

しかし、一般的な場合には、関数とは「関数本体」だけでなく、
その関数が参照する**自由変数（free lexical variables）**も含む。

このペアリングのことを **レキシカルクロージャ（lexical closure）**、または単に**クロージャ（closure）**と呼ぶ。
これは、関数の内部に自由変数が**閉じ込められている（enclosed）**ことに由来する。

---

次の例を見てみよう：

```lisp
(defun adder (c)
  "Return a function that adds c to its argument."
  #'(lambda (x) (+ x c)))

> (mapcar (adder 3) '(1 3 10)) => (4 6 13)

> (mapcar (adder 10) '(1 3 10)) => (11 13 20)
```

`adder` を異なる値の `c` で呼び出すたびに、
「`c` を引数に加える関数」という**異なる関数**が作られる。

`adder` の呼び出しごとに新しい局所変数 `c` が生成されるため、
それぞれの呼び出しで返される関数は**ユニークな関数**となる。

---

別の例を見てみよう。
関数 `bank-account` は、**銀行口座を表すクロージャ**を返す。

このクロージャは局所変数 `balance` をキャプチャしており、
クロージャの本体はその `balance` を**読み書きするコード**を提供している。

```lisp
(defun bank-account (balance)
  "Open a bank account starting with the given balance."
  #'(lambda (action amount)
      (case action
        (deposit  (setf balance (+ balance amount)))
        (withdraw (setf balance (- balance amount))))))
```

---

次の例では、`bank-account` を2回呼び出している。
それぞれが独立した `balance` の値を持つ別々のクロージャを生成する。

以降の呼び出しでは、それぞれのクロージャが独自の残高を変更するが、
2つの口座の間で混同は起こらない。

```lisp
> (setf my-account (bank-account 500.00)) => #<CLOSURE 52330407>

> (setf your-account (bank-account 250.00)) => #<CLOSURE 52331203>

> (funcall my-account 'withdraw 75.00) => 425.0

> (funcall your-account 'deposit 250.00) => 500.0

> (funcall your-account 'withdraw 100.00) => 400.0

> (funcall my-account 'withdraw 25.00) => 400.0
```

---

このような**クロージャを利用したプログラミングスタイル**については、
[第13章](chapter13.md) でさらに詳しく扱う。

## 3.17 特殊変数（Special Variables）

Common Lisp には、2種類の変数がある：
**レキシカル変数（lexical variable）** と **特殊変数（special variable）** である。

初心者にとっては、Common Lisp の「特殊変数」を
他の言語における「グローバル変数」と同一視したくなるかもしれない。
しかし、残念ながらそれは正確ではなく、混乱の原因となる。
Common Lisp の変数は、Common Lisp 独自の考え方で理解するのが最もよい。

---

### レキシカル変数（Lexical Variables）

デフォルトでは、Common Lisp の変数は **レキシカル変数** である。

レキシカル変数は、`let` や `defun` のような構文的構成（syntactic construct）によって導入される。
「レキシカル」という名前の由来は、
それらの変数が**その構文の内部（字句的範囲）に現れるコード**からのみ参照できることにある。

その構文の本体部分（body）が、その変数の **スコープ（scope）** と呼ばれる。

---

ここまでは Common Lisp と他の言語の間に違いはない。
興味深いのは、変数の **エクステント（extent：存続期間）** を考えるときである。

多くの言語では、変数のスコープとエクステントは同じである：
すなわち、ブロックに入ると新しいローカル変数が生成され、
ブロックを抜けるとその変数は消滅する。

しかし Lisp では、新しい関数（クロージャ）を生成できるため、
**変数を参照するコードが、変数のスコープを抜けた後も生き続ける**ことが可能である。

再び次の `bank-account` 関数を考えてみよう。
これは銀行口座を表すクロージャを作る関数である：

```lisp
(defun bank-account (balance)
  "Open a bank account starting with the given balance."
  #'(lambda (action amount)
      (case action
        (deposit (setf balance (+ balance amount)))
        (withdraw (setf balance (- balance amount))))))
```

この関数はレキシカル変数 `balance` を導入している。
`balance` のスコープは関数の本体部分であり、
したがって `balance` への参照はこのスコープ内でのみ可能である。

では、`bank-account` が呼び出され、その実行を終えた後はどうなるだろうか？
関数本体の実行が終わった後は、
他のコードからその特定の `balance` インスタンスを参照することはできない。

スコープは終了している。
しかし `balance` の**エクステント（生存期間）は続いている。**

私たちはそのクロージャを呼び出すことができ、
そのクロージャは `balance` を参照できる。
なぜなら、そのクロージャを生成したコードは、
`balance` のスコープ内に**字句的に存在していた**からである。

---

要約すると、Common Lisp のレキシカル変数は、
**クロージャの内部に捕捉され（captured）、スコープを離れた後も参照できる**点で、
他の言語の変数とは異なる。

---

### 特殊変数（Special Variables）

次に、**特殊変数**を考えよう。
特殊変数は `defvar` または `defparameter` によって作られる。

たとえば次のように書いたとする：

```lisp
(defvar *counter* 0)
```

これにより、プログラムのどこからでも
特殊変数 `*counter*` を参照できるようになる。
これは一見すると「グローバル変数」と同じに見える。

---

しかし重要なのは、`*counter*` の**グローバル束縛（binding）**が、
ローカルな束縛によって**一時的に隠される（shadowされる）**可能性があることだ。

多くの言語では、ローカルな束縛を導入すると
それは新しいレキシカル変数を作ることを意味する。
しかし Common Lisp では、**特殊変数はローカルにもグローバルにも束縛できる。**

次の例を見てみよう：

```lisp
(defun report ()
  (format t "Counter = ~d" *counter*))

> (report)
Counter = 0
NIL

> (let ((*counter* 100))
    (report))
Counter = 100
NIL

> (report)
Counter = 0
NIL
```

ここでは `report` が3回呼ばれている。

* 1回目と3回目の呼び出しでは、
  `report` は特殊変数 `*counter*` の**グローバル値**を出力している。

* 2回目の呼び出しでは、
  `let` フォームが特殊変数 `*counter*` に対して新しいローカル束縛を導入している。
  その結果、`report` はこのローカル値を出力する。

* `let` のスコープを抜けると、この新しい束縛は解除され、
  最後の呼び出しでは再びグローバル値が使われる。

---

要約すると、Common Lisp の特殊変数は：

* **グローバルスコープ**を持ちながら、
* **ローカル（動的）シャドウイング**を許す、という点で他の言語と異なる。

---

覚えておこう：

| 種類          | スコープ       | エクステント          |
| ----------- | ---------- | --------------- |
| **レキシカル変数** | レキシカル（字句的） | 無期限（indefinite） |
| **特殊変数**    | 無期限（グローバル） | 動的（dynamic）     |

---

### `symbol-value` によるアクセス

関数呼び出し：

```lisp
(symbol-value var)
```

ここで *var* がシンボルに評価されるとき、
そのシンボルに対応する**特殊変数の現在の値**を取得できる。

特殊変数の値を設定するには、次の2つの書き方がまったく同じ意味になる：

```lisp
(setf (symbol-value var) value)
(set var value)
```

どちらも *var* と *value* を評価する。

---

レキシカル変数に対しては、これに対応する形式は存在しない。
特殊変数だけが、**シンボルと値の対応関係（マッピング）**を
実行中のプログラムからアクセスできるようにしている。

一方、レキシカル変数（および従来の言語の変数）は、
**コンパイル時**にのみシンボル（識別子）が意味を持つ。
プログラムが実行される時点では、識別子はコンパイルによって消去されており、
変数にアクセスできるのはスコープ内のコードだけである。

---

### ■ 演習 3.6 [s]

次のようにレキシカル変数 `a` と特殊変数 `*b*` が初期化されているとする。
このとき、次の `let` フォームの値は何になるだろうか？

```lisp
(setf a 'global-a)
(defvar *b* 'global-b)

(defun fn () *b*)

(let ((a 'local-a)
      (*b* 'local-b))
  (list a *b* (fn) (symbol-value 'a) (symbol-value '*b*)))
```

## 3.18 複数値（Multiple Values）

この本全体を通して、私たちは「関数が返す値（the value returned by a function）」という表現を使ってきた。
歴史的に、Lisp は「すべての関数は値を返す」ように設計されており、
それが手続き的な処理であっても例外ではない。

しかし、**1つの関数から複数の情報を返したい場合**もある。
もちろん、リストや構造体（structure）を作ってその中に情報を格納することもできるが、
その場合は構造体を定義し、毎回インスタンスを作り、さらに分解して値を取り出す必要がある。
これは面倒である。

---

たとえば、関数 `round` を考えてみよう。
この関数は、浮動小数点数を最も近い整数に丸めるために使える。
したがって：

```lisp
(round 5.1) => 5
```

となる。

しかし、プログラマが**小数部分にも興味を持つ場合**がある。
このとき、`round` は整数値と残りの小数部分の**2つの値**を返すことで、
両方のニーズに応える：

```lisp
> (round 5.1) => 5 .1
```

---

`=>` の後に2つの値があるのは、
`round` が **2つの値（multiple values）** を返すからである。

ただし、ほとんどの場合、複数の値は無視され、**最初の値だけが使われる。**
したがって：

```lisp
(* 2 (round 5.1)) => 10
```

となり、まるで `round` が1つの値しか返さないかのように動作する。

複数の値をすべて扱いたい場合には、
`multiple-value-bind` のような特殊形式を使う必要がある。

---

```lisp
(defun show-both (x)
  (multiple-value-bind (int rem)
      (round x)
    (format t "~f = ~d + ~f" x int rem)))

> (show-both 5.1)
5.1 = 5 + 0.1
```

この例では、`round` の返す2つの値が
`int` と `rem` にそれぞれ束縛され、両方を使って出力している。

---

自分で複数の値を返す関数を定義することもできる。
そのために使うのが `values` 関数である。
`values` は与えられた引数を複数値として返す：

```lisp
> (values 1 2 3) => 1 2 3
```

---

複数値は、**必要なときにだけ使える unobtrusive（邪魔にならない）** 仕組みであり、
とても優れた解決法である。

たとえば、`round` を使うとき、
ほとんどの場合は整数値だけに興味がある。

もし `round` が複数値を使わず、
2つの値をリストや構造体にまとめて返していたら、
通常のケースでは扱いにくくなっていただろう。

---

また、`(values)` を使って**値を一切返さない関数**を作ることもできる。
これは「副作用のために呼び出される関数」（たとえば出力関数）でよく使われる。

たとえば `describe` は、
情報を出力したあと **値を返さない（no values）** ように定義されている：

```
> (describe 'x)
Symbol X is in the USER package.
It has no value, definition or properties.
```

---

しかし、`(values)` や他の「値を返さない式」が
**値が期待される文脈**の中に現れた場合、
Lisp の「1式＝1値」という原則に従い、
`nil` を返すことになる。

次の例を見てみよう。

```
> (list (describe 'x))
Symbol X is in AILP package.
It has no value, definition or properties.
(NIL)
```

ここで `describe` は値を返さないが、
`list` はその返り値を1つの値として要求するため、
結果として `nil` が返されている。

## 3.19 パラメータについての詳細（More about Parameters）

Common Lisp は、関数のパラメータを指定する方法において非常に柔軟であり、
それゆえ関数が受け取る引数の指定にも多くの自由度を提供している。

---

以下は、算術の練習を行うプログラムである。
このプログラムはユーザに *n* 個の問題を出題し、
各問題では算術演算子 `op`（`+`、`-`、`*`、`/`、あるいは他の二項演算子でもよい）をテストする。
演算子に与えられる引数は、0 から `range` までのランダムな整数である。

```lisp
(defun math-quiz (op range n)
  "Ask the user a series of math problems."
  (dotimes (i n)
    (problem (random range) op (random range))))

(defun problem (x op y)
  "Ask a math problem, read a reply, and say if it is correct."
  (format t "~&How much is ~d ~a ~d?" x op y)
  (if (eql (read) (funcall op x y))
      (princ "Correct!")
      (princ "Sorry, that's not right.")))
```

---

次はその使用例である：

```lisp
> (math-quiz '+ 100 2)
How much is 32 + 60? 92
Correct!
How much is 91 + 19? 100
Sorry, that's not right.
```

---

この `math-quiz` 関数には問題がある。
それは、ユーザが3つの引数――演算子、範囲、繰り返し回数――をすべて入力しなければならない点である。
ユーザは引数の**順序を覚え**, さらに**演算子をクォート**しなければならない。
これは、たぶん足し算を学んでいる初心者に求めるには多すぎる作業である。

---

Common Lisp には、この問題を解決するための2つの方法がある。
1つ目は、プログラマが特定の引数を *オプション（optional）* として指定し、
その引数にデフォルト値を与えることである。

たとえば、`math-quiz` において
演算子のデフォルトを `+`、数値範囲のデフォルトを `100`、問題数のデフォルトを `10` に設定するには、
次のように定義すればよい：

```lisp
(defun math-quiz (&optional (op '+) (range 100) (n 10))
  "Ask the user a series of math problems."
  (dotimes (i n)
    (problem (random range) op (random range))))
```

---

これにより、次の2つの呼び出しは同じ意味になる：

```lisp
(math-quiz)
(math-quiz '+ 100 10)
```

もしオプションパラメータが単独で現れ、デフォルト値が指定されていない場合、
その既定値は `nil` になる。

オプションパラメータは便利だが、
もしユーザが「演算子と範囲はそのままで、繰り返し回数だけ変えたい」と思った場合、
オプションパラメータは**位置依存**のため、
結局すべての引数を入力する必要がある：

```lisp
(math-quiz '+ 100 5)
```

---

Common Lisp では、**位置に依存しないパラメータ**も指定できる。
これが *キーワードパラメータ（keyword parameters）* である。

キーワードパラメータは関数呼び出し時に**明示的に名前を付けて**指定する。
通常はデフォルト値を使うが、時折だけ特定の値を使いたい場合に便利である。

たとえば、`math-quiz` を次のように定義できる：

```lisp
(defun math-quiz (&key (op '+) (range 100) (n 10))
  "Ask the user a series of math problems."
  (dotimes (i n)
    (problem (random range) op (random range))))
```

---

これで次の2つの呼び出しは同じ意味になる：

```lisp
(math-quiz :n 5)
(math-quiz :op '+ :n 5 :range 100)
```

キーワード引数は、**コロンで始まる引数名**とその値のペアで指定される。
これらのペアの順序は自由である。

---

コロンで始まるシンボルは *キーワード（keyword）* と呼ばれ、
引数リスト以外でも使用できる。

ただし、Lisp における *keyword* という用語は、
他の多くの言語における使われ方とは異なる。

たとえば Pascal では、キーワード（または *予約語 reserved words*）とは、
`if`, `else`, `begin`, `end` のような構文記号（syntactic symbols）のことである。
Lisp ではこのようなシンボルを **特殊形式演算子（special form operators）** または単に **特殊形式（special forms）** と呼ぶ。

---

Lisp のキーワードは、**keyword パッケージ**に存在するシンボルである。
これらは特別な構文的意味を持たないが、
**自己評価的（self-evaluating）** という特異な性質を持つ。
つまり、評価してもそのまま自分自身を返す定数である。
他のシンボルが変数に束縛された値を返すのとは異なる。

キーワードは `&key` 引数リストで使われるが、
それは構文上の決まりではなく、**値としての性質**によるものである。

重要なのは、**キーワードは関数呼び出しで使われるが、
関数定義では通常の非キーワードシンボルが使われる**という点である。

---

さらにややこしいことに、
シンボル `&optional`, `&rest`, `&key` は
歴史的理由により *ラムダリスト・キーワード（lambda-list keywords）* と呼ばれる。
ただし、実際には `&` に特別な意味はない。

以下に注釈付きの例を示す：

```lisp
> :xyz => :XYZ                            ; キーワードは自己評価的

> &optional =>                            ; ラムダリスト・キーワードは通常のシンボル
Error: the symbol &optional has no value

> '&optional => &OPTIONAL

> (defun f (&xyz) (+ &xyz &xyz)) => F     ; & には意味がない

> (f 3) => 6

> (defun f (:xyz) (+ :xyz :xyz)) =>
Error: the keyword :xyz appears in a variable list.
Keywords are constants, and so cannot be used as names of variables.

> (defun g (&key x y) (list x y)) => G

> (let ((keys '(:x :y :z)))              ; キーワード引数は計算によって生成できる
   (g (second keys) 1 (first keys) 2)) => (2 1)
```

---

この章で紹介した多くの関数は、
キーワード引数を取ることで柔軟に動作する。

たとえば、シーケンス中で特定の要素を探す `find` 関数を思い出してほしい：

```lisp
> (find 3 '(1 2 3 4 -5 6.0)) => 3
```

`find` はいくつかのオプションのキーワード引数を受け取る。

たとえば次のように `6` を探してみると：

```lisp
> (find 6 '(1 2 3 4 -5 6.0)) => nil
```

これは失敗する。
なぜなら、`find` は `eql` によって等価性をテストするが、
`6` は `6.0` と `eql` ではないからである。

しかし、`6` は `equalp` では `6.0` と等価であるため、
`:test` キーワードを使うことで次のように指定できる：

```lisp
> (find 6 '(1 2 3 4 -5 6.0) :test #'equalp) => 6.0
```

---

実際には、`:test` キーワードには任意の**二項述語**を指定できる。
等価性述語に限らない。

たとえば、「4 より大きい最初の数」を探すには次のように書ける：

```lisp
> (find 4 '(1 2 3 4 -5 6.0) :test #'<) => 6.0
```

---

さて、今度は数値の符号を気にしないと仮定しよう。
もし `5` を探したときに、`-5` も見つけたいとする。
これを扱うには、`:key` キーワードを使い、リスト内の各要素に `abs` 関数を適用して絶対値を取るようにすればよい。

```lisp
> (find 5 '(1 2 3 4 -5 6.0) :key #'abs) => -5
```

---

キーワードパラメータは、組み込み関数の有用性を大幅に拡張し、
ユーザが定義する関数に対しても同様の効果をもたらすことができる。
組み込み関数の中で最も一般的なキーワードは、次の2つのグループに分類される。

* `:test`, `:test-not`, `:key` — マッチング関数に使用されるもの
* `:start`, `:end`, `:from-end` — シーケンス関数に使用されるもの

いくつかの関数は、両方のキーワードセットを受け取ることができる。
（*Common Lisp the Language*, 第2版では、`:test-not` キーワードの使用は推奨されていないが、
それでも言語仕様の一部として残されている。）

---

マッチング関数には、
`sublis`, `position`, `subst`, `union`, `intersection`,
`set-difference`, `remove`, `remove-if`, `subsetp`,
`assoc`, `find`, `member` などがある。

既定では、これらの関数はある要素が一連の他のオブジェクトの1つ以上と
`eql` で等しいかどうかをテストする。

このテストは、`:test` 引数として別の述語を指定することで変更できるし、
`:test-not` を指定することで反転させることもできる。

さらに、比較をオブジェクト全体に対してではなく
オブジェクトの一部に対して行いたい場合には、
`:key` 引数としてセレクタ関数を指定することで実現できる。

---

シーケンス関数には、`remove`, `remove-if`, `position`, `find` などがある。
最も一般的なシーケンスの型はリストだが、
文字列やベクタもシーケンスとして使用できる。

シーケンス関数は、シーケンスの要素に対して繰り返し何らかの処理を行う。
デフォルトでは、シーケンスを最初から最後まで順に走査するが、
`:from-end t` を指定すれば逆順で処理することができ、
`:start` または `:end` キーワードに数値を指定すれば部分シーケンスを扱うこともできる。

なお、シーケンスの最初の要素は **1 ではなく 0** 番目である点に注意。

---

キーワードパラメータの例として、
`find` や `find-if` に似ているが、
一致する最初の要素ではなく一致する**すべての要素のリスト**を返す
シーケンス関数を書きたいとしよう。

この新しい関数を `find-all` と `find-all-if` と呼ぶことにする。

---

別の見方をすると、これらの関数は `remove` の変種である。
一致する要素を削除する代わりに、
一致する要素だけを残し、一致しないものを削除する。

このように考えると、関数 `find-all-if` は実際には `remove-if-not` と同じ関数であることがわかる。
（`not` と `null` のように）同じ関数に別の見方で2つの名前を持たせるのは便利なことがある。

新しい名前を `defun` で定義してもよいが、
定義をそのままコピーしても済む：

```lisp
(setf (symbol-function 'find-all-if) #'remove-if-not)
```

---

残念ながら、`find-all` に正確に対応する組み込み関数は存在しないので、
自分で定義しなければならない。
幸いなことに、`remove` が大部分の処理を担ってくれる。

必要なのは、`remove` に `:test` 述語の補集合を渡すようにすることだけである。

たとえば、リストの中で `1` に等しいすべての要素を見つけることは、
`1` に等しくない要素を削除することと等価である：

```lisp
> (setf nums '(1 2 3 2 1)) => (1 2 3 2 1)

> (find-all 1 nums :test #'=) ≡ (remove 1 nums :test #'/=) => (1 1)
```

---

次に必要なのは、**ある関数の補集合を返す高階関数**である。
言い換えると、`=` を与えたら `/=` を返すような関数である。

この関数は ANSI Common Lisp では `complement` と呼ばれているが、
それ以前のバージョンでは定義されていなかったため、ここに定義を示す：

```lisp
(defun complement (fn)
  "If FN returns y, then (complement FN) returns (not y)."
  ;; この関数は ANSI Common Lisp では組み込みだが、
  ;; 非ANSIコンパイラ向けにここで定義している。
  #'(lambda (&rest args) (not (apply fn args))))
```

---

`find-all` が `:test` 述語を伴って呼び出された場合、
`remove` にその補集合を `:test` として渡すだけでよい。

これは、`:test` 関数が指定されておらず `eql` がデフォルトの場合でも同様である。

また、ユーザが `:test-not` 述語を指定した場合も考慮する必要がある。
これは、述語が偽のときにマッチを成功させるために使われる。

同じ呼び出しで `:test` と `:test-not` の両方を指定するのはエラーなので、
そのケースを検査する必要はない。

その定義は次のようになる：

```lisp
(defun find-all (item sequence &rest keyword-args
                 &key (test #'eql) test-not &allow-other-keys)
  "Find all those elements of sequence that match item,
  according to the keywords.  Doesn't alter sequence."
  (if test-not
      (apply #'remove item sequence
             :test-not (complement test-not) keyword-args)
      (apply #'remove item sequence
             :test (complement test) keyword-args)))
```

---

この定義で難しいのは、パラメータリストを理解する部分だけである。
`&rest` は、すべてのキーワード／値のペアを変数 `keyword-args` に蓄積する。

`&rest` パラメータに加えて、2つの特定のキーワードパラメータ
`:test` と `:test-not` が指定されている。

パラメータリストに `&key` を含める場合、
他のキーワードも許可したいのであれば `&allow-other-keys` を付ける必要がある。
この場合、`:start` や `:key` などのキーワードを受け取り、
それらを `remove` に渡すことを意図している。

---

すべてのキーワード／値のペアはリスト `keyword-args` に蓄積され、
その中には `:test` や `:test-not` の値も含まれる。

したがって次のようになる：

```lisp
(find-all 1 nums :test #'= :key #'abs)
  = (remove 1 nums :test (complement #'=) :test #'= :key #'abs)
  => (1 1)
```

`remove` の呼び出しには2つの `:test` キーワードが含まれていることに注意。
これはエラーではない。
Common Lisp では、**左側に現れた値が優先される**と定義されている。

ラムダリストキーワードには、上級プログラマが使うものがあと2つある。

まず、マクロ定義（関数定義ではない）内では、
シンボル `&body` を `&rest` の同義語として使用できる。

違いは、`&body` は一部のフォーマットプログラムに
残りの部分を「本体（body）」としてインデントさせる点である。

たとえば次のようなマクロを定義した場合：

```lisp
(defmacro while2 (test &body body)
  "Repeat body while test is true."
  `(loop (if (not ,test) (return nil))
         . ,body))
```

自動インデント機能を持つシステムでは、
`while` よりも `while2` のほうがきれいに整形される：

```lisp
(while (< i 10)
       (print (* i i))
       (setf i (+ i 1)))

(while2 (< i 10)
  (print (* i i))
  (setf i (+ i 1)))
```

最後に、`&aux` は新しいローカル変数を束縛するために使える。
これは `let*` で束縛するのと同様である。

個人的には、`&aux` は好ましくないと思う。
なぜなら、`&aux` 変数は実際にはパラメータではなく、
パラメータリストに含めるべきではないからだ。

明示的に `let` を使ってローカル変数として区別すべきだと考える。

しかし、良いプログラマの中にも、
おそらく紙面や画面上のスペースを節約するために `&aux` を使う人がいる。
私の本心に反して、以下に例を示す：

```lisp
(defun length14 (list &aux (len 0))
  (dolist (element list len)
    (incf len)))
```

**解答 3.5**
`*db*` というデータベースを保持する。
データベースはノードの木構造として組織化されている。
各ノードには3つのフィールドがある：
そのノードが表すオブジェクトの名前、
回答が「yes」のときに進むノード、
そして回答が「no」のときに進むノードである。

ノードを順にたどっていき、
「it」という回答が得られるか、
またはあきらめなければならない地点に到達するまで続ける。
後者の場合、データベースを破壊的に変更して新しい情報を追加する。

```lisp
(defstruct node
  name
  (yes nil)
  (no nil))

(defvar *db*
  (make-node :name 'animal
             :yes (make-node :name 'mammal)
             :no (make-node
                   :name 'vegetable
                   :no (make-node :name 'mineral))))


(defun questions (&optional (node *db*))
  (format t "~&Is it a ~a? " (node-name node))
  (case (read)
    ((y yes) (if (not (null (node-yes node)))
                 (questions (node-yes node))
                 (setf (node-yes node) (give-up))))
    ((n no)  (if (not (null (node-no node)))
                 (questions (node-no node))
                 (setf (node-no node) (give-up))))
    (it 'aha!)
    (t (format t "Reply with YES, NO, or IT if I have guessed it.")
       (questions node))))

(defun give-up ()
  (format t "~&I give up - what is it? ")
  (make-node :name (read)))
```

```lisp
Is it a MAMMAL? yes

#S(NODE :NAME BEAR)

> (questions)

Is it a MAMMAL? no
I give up - what is it? penguin
#S(NODE :NAME PENGUIN)

> (questions)
Is it a ANIMAL? yes
Is it a MAMMAL? yes
Is it a BEAR? it
AHA!
```

**解答 3.6**
値は次の通りである：
`(LOCAL-A LOCAL-B LOCAL-B GLOBAL-A LOCAL-B)`。

`let` 式は `a` を**レキシカルに**束縛し、`*b*` を**動的に**束縛する。
したがって、`a` と `*b*`（および `fn` 内の `*b*` 参照を含む）への参照はすべてローカル値を得る。

`symbol-value` 関数は引数を常に**スペシャル変数**として扱うため、
`a` のレキシカルな束縛を無視し、グローバルな束縛を返す。
ただし、`*b*` の `symbol-value` はローカルな動的値である。

**解答 3.7**
2つの良い理由がある：
1つ目は、引数リストを検索する際に高速化できる点である。
最後まで探すのではなく、最初に一致したキーまで検索すればよい。
2つ目は、既存のキーワードを上書きして
引数リストを別の関数に渡したい場合、
新しいキーワード／値ペアをリストの末尾に追加するよりも
先頭に `cons` するほうが安価だからである。

---

**解答 3.9**

```lisp
(defun length-r (list)
  (reduce #'+ (mapcar #'(lambda (x) 1) list)))
```

より効率的な方法：

```lisp
(defun length-r (list)
  (reduce #'(lambda (x y) (+ x 1)) list
          :initial-value 0))
```

ANSI準拠の Common Lisp では、`:key` を指定することもできる：

```lisp
(defun length-r (list)
  (reduce #'+ list :key #'(lambda (x) 1)))
```
